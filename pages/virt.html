虚拟化与隔离

只回答三件事：怎么截获、怎么翻译、切分的代价是多少。 CPU、内存、IO 各有一套机制，GPU 是 IO 里最难的一类。

本页边界 不涉及算子与 GPU 微架构优化。只谈 hypervisor / 驱动视角： VM exit 的触发与开销、EPT 翻译路径、VFIO 与 IOMMU、virtqueue、 SR-IOV 的 PF/VF 职责、vGPU 与 SR-IOV 的隔离边界。

CPU 虚拟化

敏感指令与 trap-and-emulate

要能虚拟化，必须满足：敏感指令 ⊆ 特权指令。也就是「会暴露或改变硬件状态的指令」都要能 trap。 x86 早期不满足，反例是 popf：在不够特权级时执行它既不会 #GP，也不修改 IF， 而是静默地部分生效 —— 这类指令叫「非特权但敏感」，抓不到又跑不对。

早期解法是二进制翻译（BT）：扫描 guest 代码，把敏感指令替换成跳转。 现代硬件把这一步交给 CPU：guest 跑在 non-root，执行敏感指令时硬件自动 VM exit， hypervisor 读退出原因、模拟、再 VM entry 回去。整个过程对 guest 不可见。

追问：「有硬件辅助了，半虚拟化还有必要吗？」——有。CPU 状态可以靠硬件截获，但设备访问如果每个寄存器都 exit 仍然昂贵，所以在设备层继续用半虚拟化接口（virtio）。

三条路线

路线做法要改 guest 吗代价
全虚拟化（BT）运行时翻译敏感指令不改翻译开销大，已基本被淘汰
半虚拟化（paravirt）guest 主动发 hypercall要改内核路径短，但绑定 hypervisor
硬件辅助VT-x / SVM 提供模式与 VMCS不改exit 仍贵，但可控

现实系统是混合的：CPU 用硬件辅助，设备用 virtio。这也是 KVM 的标准形态。

追问：「paravirt 和 virtio 的思想有什么共同点？」——都让 guest 知道自己被虚拟化，用批量接口代替逐次 trap；区别是 virtio 是设备层标准，不需要改 CPU 相关代码。

VMCS 里有什么、exit 为什么贵

  • Guest-state：通用寄存器、RIP/RSP、CR0/CR3/CR4、段寄存器、MSR、活动状态。
  • Host-state：hypervisor 自己的对应状态，exit 时硬件自动加载。
  • VM-execution control：哪些事件触发 exit（MSR bitmap、I/O bitmap、EPTP、异常 bitmap、中断是否 exit）。
  • VM-exit information：basic exit reason（16 位）、qualification、中断信息、指令长度。

常见 exit 原因：CPUID、HLT、I/O 指令、MSR 读写、CR 访问、VMCALL、EPT violation、EPT misconfig、外部中断（若配置为 exit）、PAUSE（若开启）。

开销来源是复合的：硬件要保存/恢复上百个字段（VMCS 访存是内存操作）；可能刷 TLB 或破坏流水线；退出后走 hypervisor 的 C 路径（可能加锁、可能调度）；cache 被污染。所以优化方向永远是减少 exit 次数，而不是让 exit 更快。

追问：「具体怎么减少 exit？」——EPT 消除页表写保护 trap；大页减少 EPT violation；MSR bitmap 放行无害 MSR；halt polling 处理空闲；posted interrupt / APICv 投递中断；virtio 批量提交设备请求。

KVM 架构

kvm.ko + QEMU 两层

┌────────────────────────────────────────────┐
│ QEMU（用户态 VMM）                          │
│  设备模拟 / 内存布局 / 迁移 / 每 vCPU 一线程  │
├────────────────────────────────────────────┤
│ /dev/kvm  ← ioctl                          │
├────────────────────────────────────────────┤
│ kvm.ko：VMX/SVM 的薄封装、EPT、中断注入       │
├────────────────────────────────────────────┤
│ Linux：调度器、内存管理、IOMMU、设备驱动       │
├────────────────────────────────────────────┤
│ 硬件：VT-x / SVM / EPT / VT-d               │
└────────────────────────────────────────────┘

KVM 本身不实现调度和内存管理，它把 Linux 内核变成 hypervisor：vCPU 用普通调度器调度，guest 内存就是 host 进程的地址空间。这是它与 Xen（自带调度器与内存管理）最本质的区别。

追问：「这个设计带来什么限制？」——guest 看到的是 Linux 的调度与内存语义；实时性和确定性受宿主影响，所以低延迟场景要给 vCPU 绑核、配 cpuset、用 isolcpus。

/dev/kvm 的 ioctl

int kvm  = open("/dev/kvm", O_RDWR);
int vm   = ioctl(kvm, KVM_CREATE_VM, 0);

// guest 物理内存：GPA → host 进程虚拟地址
struct kvm_userspace_memory_region r = {
    .slot = 0, .guest_phys_addr = 0,
    .memory_size = 1UL << 30,
    .userspace_addr = (unsigned long)mem,
};
ioctl(vm, KVM_SET_USER_MEMORY_REGION, &r);

int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
int sz = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
struct kvm_run *run = mmap(0, sz, PROT_READ|PROT_WRITE, MAP_SHARED, vcpu, 0);

for (;;) {
    ioctl(vcpu, KVM_RUN, 0);          // 不返回 = guest 在跑
    switch (run->exit_reason) {
    case KVM_EXIT_IO:       /* PIO */
    case KVM_EXIT_MMIO:     /* MMIO */
    case KVM_EXIT_HLT:      /* 等中断 */
    }
}
容易答错的点 VM exit ≠ 回到 QEMU。大多数 exit（EPT violation、外部中断、MSR）在内核里就处理完并重新 entry； 只有需要设备模拟的才返回用户态。被问到「一次 MMIO 的路径」时要把这个区分说清楚。

追问：「KVM_RUN 内部做了什么？」——保存 host 上下文、加载 guest 状态、执行 VMLAUNCH/VMRESUME；硬件在 guest 模式运行，直到 exit 条件成立，再回到内核的 exit handler。

vCPU 就是一个普通线程

  • QEMU 为每个 vCPU 建一个 pthread，循环调 KVM_RUN，所以能看到它的 tid、能 taskset、能 perf、能绑 NUMA 节点。
  • guest 在 non-root 模式执行流仍是这个 host 线程；宿主时钟中断或 preemption timer 到来时，hypervisor 可以获得控制权，再让调度器抢占。
  • 每个 vCPU 有独立 fd，所以能通过 KVM_GET_REGS / KVM_SET_REGS 直接读写寄存器（调试和热迁移都靠它）。

追问：「vCPU 超配会怎样？」——多个 vCPU 线程抢物理核，guest 内表现为 steal time 上升、延迟抖动变大；对延迟敏感的服务要 1:1 绑核。

内存虚拟化

GVA → GPA → HPA

GVA ──guest 页表（guest 自己管，CR3）──► GPA
GPA ──EPT / NPT（hypervisor 管）──────► HPA

关键在于两层页表归属不同：guest 管 GVA→GPA，hypervisor 管 GPA→HPA。 所以 guest 改自己的页表不需要通知 hypervisor —— 这正是 EPT 的根本优势。

追问：「EPT 页表本身放在哪？」——放在 host 物理内存，由 hypervisor 分配；EPTP 含在 VMCS 的 VM-execution control 里，VM entry 时硬件从那里取。

影子页表 vs EPT

维度影子页表EPT / NPT
翻译执行者hypervisor 软件拼表硬件两级遍历
guest 改页表页表页设只读，写触发 trap 再同步不拦截
内存开销每个 guest 进程一套每个 VM 一套
缺页信息只有 guest page fault，需推断violation 直接给出 GPA 与访问类型

一句话总结：EPT 把「同步两套页表」这个难题从 hypervisor 里删掉了，代价是 TLB miss 时要多走一遍页表。

追问：「那 EPT 的代价具体是什么？」——最坏情况下一次 guest 访存要遍历两套页表，访存次数成倍增加；靠 TLB、paging-structure cache 和 2MB/1GB 大页缓解。

EPT violation 怎么处理

硬件给出的 exit qualification 足以判断三件事：GPA 是多少、是读/写/执行、是缺页还是权限违规。

  1. 普通内存缺页：分配 host page，填 EPT entry，重新 entry。
  2. MMIO 地址：交给设备模型模拟（例如 virtio 的 doorbell），不分配内存。
  3. 越界或权限错误：注入异常或终止 VM。

最坏路径的访存量是两级页表深度相乘：guest 每取一个页表项，这个页表项本身还要经 EPT 翻译才能读到，所以 4 级 guest 遍历 × 4 级 EPT 遍历，最坏是十几次访存，再加最终数据访问。实际靠 TLB、paging-structure cache 和 2MB/1GB 大页把它压下来 —— 别背精确数字，背「深度相乘、靠缓存和大页缓解」。

追问：「怎么区分 MMIO 的 violation 和内存缺页？」——看 GPA 是否落在某个 memory region 之外、是否命中设备 BAR；KVM 用 memslot 和 KVM_EXIT_MMIO 来处理后者。

内存回收：balloon 与 KSM

  • Ballooning：guest 内装 balloon 驱动，hypervisor 让它「充气」——guest 主动交出一批页并报告页号，hypervisor 回收。是协作式回收，依赖 guest 驱动。
  • KSM：host 扫描匿名页，内容相同的合并为一页、写时复制。省内存，但持续扫描耗 CPU。
  • Swap：把 guest 内存换到磁盘，延迟从微秒级变成毫秒级，通常是最不得已的手段。

追问：「KSM 有什么安全风险？」——同页合并意味着「别人有没有这块内容」可能通过访问时序泄露，构成跨 VM 侧信道；生产环境常关闭 KSM。

设备虚拟化

全模拟

guest 用真实设备驱动（如 e1000），每次寄存器访问触发 VM exit，由 QEMU 解析并改设备状态。最慢，但不需要 guest 装任何特殊驱动，兼容性最好；用于启动阶段和无法改 guest 的场景。

追问：「都什么年代了还用全模拟？」——装 OS 时还没有 virtio 驱动；老系统迁移；以及作为 virtio 的兜底。

virtio：virtqueue 与 kick

split virtqueue 由三块共享内存组成，读写者严格分离：

区域每项大小谁写内容
Descriptor table16 字节 × 队列长度driver 建链，device 只读addr / len / flags / next
Available ring6 + 2 × 队列长度driver 写，device 读idx 递增，指向请求链头
Used ring6 + 8 × 队列长度device 写，driver 读完成的链头与实际长度
 
/* driver 侧：把链头挂到 available ring */
avail->ring[avail->idx % qsz] = head_desc;
avail->idx++;                    // 只递增，不回退
wmb();                           // 保证 desc 先可见，再发通知
iowrite16(0, queue_notify);      // 写队列号 = available buffer notification

注意 avail->idx 是单调递增的计数器，取模只用于定位槽位；device 靠它和 used ring 的 idx 判断有多少新请求。通知前必须有内存屏障，否则 device 可能先看到 idx 更新、再去读还没写完的 descriptor。

性能优势的本质是exit 次数的量级变化：全模拟是「每次寄存器写一次 exit」，virtio 是「一批请求一次通知」。后端可以放进内核（vhost-net）或独立进程（vhost-user），进一步减少 QEMU 参与。

追问：「kick 能省掉吗？」——能。用 EVENT_IDX 做通知抑制，或干脆轮询（busy-poll，DPDK/SPDK 的做法），用 CPU 换延迟。

直通：VFIO + IOMMU

host 上由 vfio-pci 接管设备，guest 装原生驱动直接访问 BAR。DMA 地址由 IOMMU 翻译，所以 guest 只能碰 hypervisor 映射给它的内存。性能接近原生，但设备被独占、不能迁移、host 不能再驱动它。

追问：「为什么直通设备不能热迁移？」——hypervisor 看不到设备内部状态（队列、页表、固件），而且可能有 DMA 在途；没有可序列化的状态就没有迁移。

SR-IOV：PF 与 VF

  • PF：完整 PCIe 功能，PF 驱动跑在 host，负责创建/销毁 VF、配置 VLAN/MAC/QoS、处理 mailbox。
  • VF：轻量 PCIe 功能，有独立配置空间、BAR、MSI-X 表和独立 BDF；VF 驱动跑在 guest，数据面不经过 PF 驱动。
  • 数量：由 SR-IOV Capability 的 InitialVFs / TotalVFs 字段声明，设备间差异很大；不要背固定上限。
  • 隔离边界：PCIe 功能视图是硬件隔离的；GPU 执行引擎在 SR-IOV 下仍是时间片共享，所以 SR-IOV 不等于性能隔离。

追问：「VF 还能再切吗？」——不能，VF 是叶子。要在更细粒度共享，用容器透传或 MIG。

四种方式对比

方式数据面路径性能隔离迁移
全模拟每次访问 exit 到 QEMU低强好
virtio共享内存 ring + 通知较高强好
直通guest 直达，IOMMU 翻译接近原生强（需 IOMMU）不支持
SR-IOV每 VF 独立硬件队列接近原生硬件隔离不支持

追问：「virtio 和 SR-IOV 怎么选？」——要超配、要迁移、不依赖硬件，选 virtio；要极致性能和硬件隔离，选 SR-IOV。很多云是控制面 virtio、数据面 SR-IOV。

IOMMU

DMA remapping 与 IOMMU group

没有 IOMMU 时，设备发出的地址就是物理地址，设备能写哪里完全取决于驱动给它的地址。开了 IOMMU 后设备发 IOVA，经页表译为 HPA，于是获得三个能力：越界 fault、地址空间独立、支持大页。

IOMMU group 是「能与其他设备隔离的最小集合」，也是 VFIO 的所有权单位。同一 group 内的设备必须一起交给 VFIO，因为硬件无法区分它们之间的 DMA（常见原因是缺 ACS 的 PCIe 桥或多功能设备）。

追问：「group 里有两个设备，能只直通一个吗？」——不能，除非拓扑允许拆 group（例如换插槽、开启 ACS 重定向）。

中断重映射

MSI/MSI-X 的本质是设备往一个地址写数据，这个地址被解释为「向量 + 目标 CPU」。若 guest 能控制它，就能伪造任意中断、注入到别的 VM。中断重映射让设备写的是 interrupt handle，由 IOMMU 查表决定真实目标，guest 无法构造任意中断。

安全上最重要的是 DMA remapping：它决定设备能碰哪块物理内存。但要防止 guest 伪造中断注入到别的 VM，还需要中断重映射。两者的关系是：DMA remapping 是直通能成立的前提，中断重映射是多租户场景下的加固。补充一个边界：VFIO 有 no-IOMMU 模式，但它是给「用户态驱动、明确接受不安全 DMA」的场景，不能用于多租户直通。

追问：「posted interrupt 和中断重映射什么关系？」——posted interrupt 是 VT-d 的中断投递优化，直接写 guest 的 posted-interrupt descriptor，避免为了注入中断而 exit；它建立在中断重映射的翻译框架上。

ATS 与 PRI

  • ATS：设备侧缓存翻译结果（ATC），像 TLB；命中就不走 IOMMU，降低延迟。代价是页表改动后要发 ATC invalidation 保持一致。
  • PRI：设备缺页时可以向 host 发页请求，而不是直接失败。这是 Shared Virtual Memory 的基础 —— CPU 和 GPU 共享同一套虚拟地址，GPU 缺页时按需换入。

追问：「ATC 不失效会怎样？」——设备用到过期的翻译，DMA 写到错误的物理页，属于数据损坏级 bug，而且极难复现。

GPU 虚拟化

vGPU：hypervisor 时间片

hypervisor 里跑 vGPU manager，把物理 GPU 按时间片分给多个 VM；guest 装厂商的 vGPU 驱动。可以超配，部分产品支持迁移，但性能有明显损失，且依赖 license 与 hypervisor 支持。

追问：「vGPU 的切换和 CPU 进程切换差在哪？」——GPU 上下文大得多（寄存器、页表、显存映射、引擎状态），切换成本高，所以调度粒度通常是毫秒级，远大于 CPU 的调度粒度。

SR-IOV：功能级切分

GPU 在硬件上实现多个 VF，每个 VF 有独立 BAR 和中断，直接分给 VM。数据面绕过 hypervisor，性能接近原生。NVIDIA 从 Ampere 起支持。

关键区别：SR-IOV 切的是 PCIe 功能视图，GPU 执行引擎默认仍是时间片共享；真正把 SM、L2、显存控制器切开的是 MIG。所以「SR-IOV = 性能隔离」是错的。

追问：「那 SR-IOV 的隔离边界到底在哪？」——配置空间、BAR、MSI-X、错误上报是硬件隔离的；执行资源和显存带宽是共享的。安全隔离成立，性能隔离不成立。

直通：整卡独占

用 VFIO 把整块 GPU 交给一个 VM，性能 100%，隔离最强，但一块卡只能给一个 VM，且不能迁移。AI 训练集群里最常见 —— 训练任务本来就占满整卡。

追问：「直通的 VM 里能用 vGPU 的功能吗？」——不能。直通装的是原生驱动，vGPU 装的是 vGPU 驱动，两条软件栈互斥。

MIG：GPU 内部分区

MIG 在 GPU 内部切分 SM slice、L2 slice、显存控制器与显存容量，instance 之间是硬件分区，隔离性与性能可预测性都好于时间片。切片数量由 GPC 数量决定（A100 为 7 个），每个 slice 还能再切成更小的 compute instance；具体上限以对应型号的官方文档为准。

MIG 不改变 PCIe 功能视图，所以它主要在容器 / K8s 场景使用；给 VM 用需要额外的支持。

追问：「MIG 和 SR-IOV VF 的本质区别？」——MIG 切的是执行资源（SM/L2/显存控制器），VF 切的是PCIe 功能；一个实例 OOM 不会影响另一个，这是硬件分区带来的。

四方案对比

方案切分层隔离性能迁移典型场景
vGPUhypervisor 时间片软件隔离有损失部分支持VDI、图形工作站
SR-IOVPCIe VF功能隔离、资源共享接近原生不支持多租户推理
直通整卡最强原生不支持训练、HPC
MIGGPU 内部 SM/显存硬件分区接近原生不支持容器共享

追问：「为什么没有一种方案同时满足弹性、性能和迁移？」——弹性要求资源可分时复用（时间片），性能要求资源独占（硬件分区），迁移要求状态可序列化。三者互相制约，这正是 GPU 虚拟化难的根本原因。

GPU 迁移为什么难

  1. 显存状态：几十 GB 需要脏页跟踪与迭代拷贝，GPU 侧没有和 CPU 等价的脏位机制。
  2. 正在跑的 kernel：必须先 quiesce（停 stream、等 kernel 完成），停机时间直接计入迁移时间。
  3. PCIe 状态：配置空间、BAR、MSI-X、FLR 语义，换机器后 BDF 可能变化，需要重建。
  4. 设备内部状态：GPU 页表、TLB、上下文、固件状态、copy engine 队列。

追问：「为什么 vGPU 能迁移，直通不能？」——vGPU 的状态由 vGPU manager 掌握，有脏页跟踪和状态序列化接口；直通把物理设备整个交出去，hypervisor 看不到内部状态。谁能序列化状态，谁就能迁移。

容器与隔离

namespace：看得见什么

namespace隔离内容表现
mnt挂载点独立根文件系统
pid进程 ID容器内 1 号进程是应用
net网络栈、网卡、端口独立 IP 与 lo
ipcSystem V IPC、POSIX 消息队列不能直接共享内存段
utshostname / domain name独立主机名
userUID / GID 映射容器 root 可映射为宿主普通用户

另有 cgroup namespace（隔离 cgroup 视图）和 time namespace（隔离时钟偏移）。创建接口是 clone(CLONE_NEW*) 或 unshare。

追问：「namespace 能限制 CPU 吗？」——不能。namespace 只改变可见性，限制资源要用 cgroup，两者正交。

cgroup：能用多少

  • v1：每个子系统一棵独立的树，同一进程在不同树里的位置不一致，管理复杂。
  • v2：统一层级，所有控制器挂在一棵树上，逐层通过 cgroup.controllers / cgroup.subtree_control 启用。
  • 常用接口：cpu.max（带宽）、memory.max（硬限制，超了 OOM）、memory.high（软限制，超了节流并回收）、io.max、pids.max。

追问：「memory.high 和 memory.max 的区别？」——high 是软限，超过后内核会节流并积极回收，尽量不杀进程；max 是硬限，超过直接触发 OOM。生产上常用 high 做缓冲。

容器 vs 虚拟机

维度容器虚拟机
内核共享宿主内核独立内核
隔离机制namespace + cgroup + capability/seccomp/LSM硬件虚拟化 + hypervisor
启动毫秒级秒级到分钟级
隔离强度弱，内核漏洞可能逃逸强，硬件边界
运行态迁移困难成熟

「共享内核」是所有差异的根源。折中方案：Kata Containers（容器外套轻量 VM）、gVisor（用户态内核拦截系统调用）。

追问：「容器逃逸的常见路径？」——特权容器 + 宿主机设备/路径挂载、内核漏洞提权、可写的 /proc/sys 或 /sys、以及历史上 cgroup release_agent 一类配置错误。

GPU 容器：透传，不是虚拟化

容器里看到 GPU，靠的是把宿主设备和驱动「注入」进去，共有四步：

  1. 设备节点：/dev/nvidia0、/dev/nvidiactl、/dev/nvidia-uvm。
  2. 驱动库：libcuda.so、libnvidia-ml.so、nvidia-smi，版本必须与宿主驱动匹配。
  3. device cgroup 放行设备号（v1 用 devices.allow，v2 用 eBPF）。
  4. nvidia-container-toolkit 通过 OCI hook 在容器启动时完成上述注入。
nvidia-smi -L                       # host 上的物理 GPU
docker run --gpus all nvidia/cuda:12.4-base nvidia-smi
# 本质：--device /dev/nvidia* + 注入驱动库 + device cgroup 放行
易错点 容器里的 nvidia-smi 看到的是宿主物理 GPU，不是虚拟设备； 默认情况下还能看到别的容器在跑的进程。这正是「容器隔离弱于 VM」在 GPU 上的体现。

追问：「多个容器怎么安全共享一块 GPU？」——device cgroup 只做访问控制，不做资源隔离；要隔离用 MIG（硬件分区），要限额用 MPS 或时间片，但都弱于 VM。

高频问答

为什么设备直通必须开 IOMMU？
  • DMA 翻译：没有 IOMMU 时，设备发出的地址被当作物理地址，guest 驱动可以 DMA 到宿主任意内存，包括内核代码页。
  • 越界保护：有 IOMMU 时 guest 只能访问被映射的 IOVA，越界触发 IOMMU fault，可以只杀这个 VM。
  • 中断重映射：MSI 本质是设备写地址触发中断，不重映射的话 guest 能伪造中断注入别的 VM。
  • IOMMU group：它是 VFIO 的所有权单位，同 group 设备必须整体交给 VFIO。

补充：VFIO 存在 no-IOMMU 模式，但仅用于明确接受不安全 DMA 的用户态驱动场景，不能用于多租户直通。

virtio 为什么比全模拟快？
  • exit 批量化：全模拟是每个寄存器访问一次 exit；virtio 是一批请求一次 available buffer notification。
  • 共享内存：descriptor table、available ring、used ring 都在 guest 与 host 共享的内存里，不需要每次陷入。
  • 无锁的单生产者单消费者：driver 只写 available ring，device 只写 used ring，不需要每次进 hypervisor 同步。
  • 后端可下沉：vhost-net 把后端放进内核，vhost-user 放进独立进程，减少 QEMU 参与。

本质是 exit 数量的量级下降，不是「模拟得更快」。

EPT 相比影子页表的优势？
  • 不拦截 guest 页表写：影子页表要把页表页设为只读，每次修改都 trap 并同步影子表；EPT 下 guest 随意改，硬件翻译时自动生效。
  • 内存开销解耦：影子页表每个 guest 进程一套，EPT 每个 VM 一套。
  • 缺页信息精确：EPT violation 直接给出 GPA、访问类型、是缺页还是权限问题。
  • 实现简单：hypervisor 里那套极其复杂的同步逻辑消失了。

代价：TLB miss 时多遍历一套页表，所以大页和 TLB 优化在虚拟化环境收益很大。

vGPU 和 SR-IOV 怎么选？
  • vGPU：需要超配（一块卡分给多个用户）、需要迁移、能接受性能损失，典型是 VDI 与图形工作站。
  • SR-IOV：VM 数量固定、要接近原生性能和硬件隔离、不需要迁移，典型是多租户推理。
  • 直通：任务占满整卡，追求最强隔离与原生性能，典型是训练和 HPC。
  • MIG：容器 / K8s 里多个小任务共享大卡，要硬件分区的隔离和可预测性。

一句话：要弹性选 vGPU，要性能选 SR-IOV / 直通，要容器内硬件隔离选 MIG。

容器里的 GPU 是怎么看到的？
  1. 注入设备节点：/dev/nvidia0、/dev/nvidiactl、/dev/nvidia-uvm。
  2. 注入驱动库：libcuda.so、libnvidia-ml.so、nvidia-smi，版本需与宿主驱动匹配。
  3. device cgroup 放行设备号（v1 devices.allow，v2 eBPF）。
  4. nvidia-container-toolkit 用 OCI hook 在容器启动时完成以上步骤。

所以容器里是真实物理 GPU，没有驱动虚拟化层；隔离依赖 device cgroup 与 MIG。

VM exit 太多，怎么定位？ 
perf kvm stat live                     # 实时看 exit reason 分布
perf kvm stat record -a sleep 10
perf kvm stat report                   # 按 reason 聚合
perf record -e kvm:kvm_exit -a sleep 10

按 reason 对症：

  • EPT_VIOLATION 多 → 检查大页、缺页频率、NUMA 配置。
  • IO_INSTRUCTION / MMIO 多 → 设备是全模拟，换 virtio。
  • MSR_WRITE 多 → guest 轮询 MSR，用 MSR bitmap 放行。
  • HLT 多 → 空闲循环，开 halt polling。
  • 外部中断多 → 考虑 posted interrupt、APICv、vCPU 绑核。

还可以看 /sys/kernel/debug/kvm/ 下的计数器和 ftrace 的 kvm_exit tracepoint。

SR-IOV 的 PF 和 VF 是什么关系？
  • PF：完整 PCIe 功能，驱动在 host，负责创建/销毁 VF、配置 VLAN/MAC/QoS、处理 mailbox。
  • VF：轻量 PCIe 功能，有独立配置空间、BAR、MSI-X 和独立 BDF；驱动在 guest，数据面不经过 PF 驱动。
  • 数量：由 SR-IOV Capability 的 InitialVFs / TotalVFs 声明，设备间差异大。
  • 依赖：PF 故障会影响其下所有 VF，所以 PF 通常由云厂商控制，不交给租户。

注意：SR-IOV 切的是 PCIe 功能视图，GPU 执行引擎仍是时间片共享，不是性能隔离。

GPU 直通后宿主机还能不能用 nvidia-smi？

宿主机上不能正常用：设备已被 vfio-pci 绑定，NVIDIA 驱动没有接管，nvidia-smi 看不到它。

  • 验证直通：lspci -k -s <BDF> 应显示 Kernel driver in use: vfio-pci。
  • guest 里装完整驱动后 nvidia-smi 正常，看到的就是物理卡。
  • vGPU 场景不同：host 上装的是 vGPU manager，可以通过它看到各 VM 的 vGPU 实例。

想监控直通卡的功耗/温度，只能走 BMC/IPMI 等带外通道，因为 host 驱动栈已经不碰这块设备。
