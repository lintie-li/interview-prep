TCP 状态机与握手挥手

三次握手：只补最容易被问倒的点

会问：为什么不能两次？四次行不行？ISN 为什么随机？

两次握手的问题不是「同步不了序号」——序号在 SYN 和 SYN-ACK 里已经各带了一个。 真正的问题是服务端无法确认客户端收到了 SYN-ACK：这个包丢了，服务端会单方面认为连接已建立并分配资源， 客户端却还在重传 SYN。多出的第三次 ACK 就是让服务端确认「对端已就绪」。 另一层作用是拒绝网络里滞留的旧 SYN：客户端用序号判断这不是本次连接，回 RST。 

CLOSED ──主动打开/SYN──► SYN_SENT ──收 SYN+ACK/回 ACK──► ESTABLISHED
CLOSED ──被动打开/收 SYN,回 SYN+ACK──► SYN_RCVD ──收 ACK──► ESTABLISHED
                                                    ▲
                        同时打开（少见）: SYN_SENT 收 SYN 不回 ACK 而回 SYN

ISN 随机不是为了安全（那是加密的事），而是避免与旧连接的序号空间重叠， 再加上 timestamp 的 PAWS 机制，才能可靠地区分新旧报文。

追问：SYN 丢了会怎样？—— 客户端指数退避重传（1s、2s、4s…），默认 6 次后放弃，约 127 秒。服务端侧如果 SYN-ACK 丢了，由 tcp_synack_retries 控制。

SYN flood 与 SYN cookie

会问：SYN flood 打的是什么资源？SYN cookie 怎么做到不存状态？

半连接（SYN_RCVD）是要占内核对象的：request_sock。攻击者伪造源 IP 发大量 SYN、 不回最后的 ACK，这些半连接把资源耗尽，正常握手进不来。

SYN cookie 的做法是不分配 request_sock：收到 SYN 时，用 「源 IP、源端口、目的 IP、目的端口 + 一个每秒轮换的密钥」做哈希，取其中 24 位， 加上 5 位时间槽和 3 位 MSS 索引，拼成 32 位塞进 SYN-ACK 的 seq。 客户端回来的 ACK 里 seq = cookie + 1，服务端重算哈希校验，通过才创建连接。

  • net.ipv4.tcp_syncookies：1 = 队列溢出时才启用（默认），2 = 强制。
  • 代价：cookie 模式下放不下 window scaling / SACK 等 option，功能退化，所以只在压力下用。
  • 半连接数量上限受 tcp_max_syn_backlog 约束；全连接（已完成握手待 accept）受 min(somaxconn, listen_backlog) 约束。

追问：SYN cookie 能防什么、不能防什么？—— 防的是「伪造源 IP 的资源耗尽」，防不了真实 IP 的洪水（那要靠限速、清洗、anycast）。

四次挥手与 TIME_WAIT 的两个作用

会问：为什么是四次？TIME_WAIT 为什么必须是 2MSL？

全双工，两个方向要分别关闭：FIN → ACK → FIN → ACK。主动关闭方发完最后一个 ACK 后进入 TIME_WAIT，等 2MSL（Linux 固定 60 秒）。

两个作用，必须完整说出来 ① 保证最后的 ACK 能到达对端。ACK 丢了，对端会重传 FIN；还在 TIME_WAIT 就能重新 ACK。 如果已经 CLOSED，收到重传的 FIN 只能回 RST，对端就不是正常关闭。
② 让旧连接的报文彻底消失。2MSL 覆盖「ACK 过去 + FIN 回来」的最坏往返， 保证相同四元组的新连接不会收到旧连接的残留报文。

为什么是 2 倍：最坏情况是 ACK 单向耗时 1 MSL、对端重传的 FIN 回来再耗 1 MSL。Linux 把 MSL 定为 30 秒， 于是 TIME_WAIT 恒为 60 秒，tcp_fin_timeout 改的是 FIN_WAIT_2，不是 TIME_WAIT。

追问：为什么 TIME_WAIT 在主动关闭方？—— 因为它是最后一个发 ACK 的人，只有它需要「万一 ACK 丢了还能重发」。被动关闭方不需要。

TIME_WAIT 过多 vs CLOSE_WAIT 堆积

会问：线上 TIME_WAIT 几万个，怎么处理？CLOSE_WAIT 很多说明什么？

状态谁造成的本质处置
TIME_WAIT本机主动关闭短连接太多、连接周转太快连接池 / keep-alive；客户端侧 tcp_tw_reuse=1；服务端 SO_REUSEADDR
CLOSE_WAIT本机被动关闭应用没调 close()，连接泄漏改代码。检查 recv()==0 后是否关闭、异常分支是否漏 fd、fd 是否被别处持有

ss -tan state time-wait | wc -l
ss -tan state close-wait | head
lsof -p <pid> | wc -l              # 对照 /proc/<pid>/limits 的 open files
  • tcp_tw_reuse=1：只对主动发起的新连接有效，且依赖 tcp_timestamps=1（默认开）。NAT 环境慎用。
  • tcp_tw_recycle：4.12 已从内核移除，别答。
  • 调小 tcp_fin_timeout 不影响 TIME_WAIT，只影响 FIN_WAIT_2，别答错。
  • 真正的解法是减少短连接，不是调参数。

追问：TIME_WAIT 会不会占满端口？—— 会。主动连接方用尽 ip_local_port_range 后无法建新连接，报 Cannot assign requested address。这时看的是本机作为客户端的连接行为。

拥塞控制

慢启动、拥塞避免、快重传、快恢复

会问：cwnd 和 ssthresh 怎么变？为什么超时和 3 个 dup ACK 的惩罚不一样？

  • 慢启动（cwnd < ssthresh）：每收一个 ACK，cwnd += 1 MSS，效果是每个 RTT 翻倍。起点是 IW10 = 10 MSS。
  • 拥塞避免（cwnd ≥ ssthresh）：每 RTT +1 MSS，线性增长（AIMD 的加性增）。
  • 超时：ssthresh = cwnd / 2，cwnd = 1 MSS，回到慢启动。最重的惩罚。
  • 快重传：收到 3 个重复 ACK，立刻重传缺失段，不等 RTO。
  • 快恢复：ssthresh = FlightSize / 2，cwnd = ssthresh + 3 MSS（3 个 dup ACK 代表 3 个包已离开网络），然后进入拥塞避免。

为什么区别对待：超时意味着连 ACK 都回不来了，网络可能严重拥塞；而 3 个 dup ACK 说明后续包还在到达， 网络只是丢了个别包，所以没必要退到 1。 

# Reno 的 cwnd 轨迹（白板要能画）
      超时:      ssthresh=cwnd/2, cwnd=1
   3 dup ACK:     ssthresh=cwnd/2, cwnd=ssthresh+3MSS
   每 RTT:        slow start 翻倍 → 到达 ssthresh → 每 RTT +1 MSS

追问：SACK 改变了什么？—— 接收方通过 SACK option 报告收到的区间，发送方一个 RTT 可以补多个洞；没有 SACK 时（NewReno）一个 RTT 通常只能恢复一个丢包。

Reno → CUBIC → BBR：差在「用什么信号判断拥塞」

会问：Linux 默认是什么？BBR 和 CUBIC 的本质区别？

算法拥塞信号窗口增长问题/场景
Reno丢包AIMD，每 RTT +1 MSS高 BDP 下恢复太慢
CUBIC（Linux 默认）丢包以「上次拥塞点」为锚的三次函数，与 RTT 无关把非拥塞丢包误判为拥塞
BBR不靠丢包，靠带宽和 RTT 估计维持 cwnd = BtlBw × RTprop，用 pacing 控制发送节奏与其他 BBR 流竞争公平性有争议；浅 buffer 下优势明显

CUBIC 解决的问题：Reno 的窗口增长依赖 RTT，RTT 越长增长越慢，导致同一条链路上短 RTT 流占便宜。 CUBIC 改成按时间增长，并且靠近上次拥塞点时增长慢、远离时增长快。

BBR 解决的问题：丢包 ≠ 拥塞。它周期性地测量两个量： BtlBw（一段时间内 ACK 反映出的最大交付速率）和 RTprop（一段时间内的最小 RTT， 即排队为空的物理时延），然后让在途数据量贴着 BDP = BtlBw × RTprop，并加一点 pacing。

为什么数据中心/长肥管道偏爱 BBR 交换机 buffer 浅，CUBIC 一丢包就砍半，吞吐周期性塌陷；BBR 不把丢包当信号，能把排队压到很低同时保持吞吐。 但在有随机丢包的无线链路上，BBR 也可能过度乐观；在完全无损的 IB 网络上，瓶颈根本不在拥塞控制。 没有银弹，只有权衡。

追问：怎么查看和切换？—— sysctl net.ipv4.tcp_congestion_control，可用的在 /proc/sys/net/ipv4/tcp_available_congestion_control；ss -i 能看到每条连接的 cwnd、rtt、拥塞算法。

追问：rwnd 是怎么算出来的？—— 接收方用「socket 接收缓冲区剩余空间」减去一些保留量，再按 window scaling 右移后填进 16 位字段。缓冲区越小，窗口越小，吞吐上限 = rwnd / RTT。

零窗口探测与糊涂窗口综合征

会问：接收缓冲满了会怎样？什么是 SWS？Nagle 和延迟 ACK 为什么要小心一起用？

  • 零窗口：接收方通告 window=0，发送方停止发送。之后接收方腾出空间时发的 window update 可能丢失， 所以发送方用 zero window probe 定时发 1 字节探测，逼对方回当前窗口。
  • SWS（糊涂窗口）：接收方每次只腾出几字节就通告，发送方就发一个「头 40 字节、载荷几字节」的小包。 对策两端都有：接收方等窗口够大（或超时）再通告；发送方用 Nagle 合并小包。
  • Nagle + 延迟 ACK：发送方等 ACK 才发下一个包，接收方等 40 ms 攒够再 ACK，两者叠加会造成明显延迟。 这就是低延迟 RPC 设 TCP_NODELAY 的原因。

追问：什么时候该关 Nagle？—— 小消息、低延迟、请求-响应模式的协议（Redis、gRPC、游戏）关；大块批量传输保持开启，让内核合并。

Linux 内核网络栈（重点）

sk_buff：为什么能前后伸缩

会问：一个报文在内核里是什么结构？为什么要预留 headroom？

整个内核网络栈用一个 struct sk_buff 表示一个报文，从驱动收到应用读走，都是同一个 skb 在流动。 关键是指针： 

struct sk_buff {
    char *head, *data, *tail, *end;  // 缓冲区起止 + 当前数据起止
    unsigned int len;              // 总长度
    struct sock *sk;               // 关联的 socket（后段才有）
    struct skb_shared_info *shinfo; // 尾部：frags、GSO 信息
};
  • skb_reserve()：把 data/tail 同时后移，预留头部空间（收包时一次留够 L2/L3/L4 的头）。
  • skb_push() / skb_pull()：在头部加 / 去一层协议头，只是移动 data 指针，O(1)，不搬数据。
  • skb_put() / skb_trim()：在尾部加 / 减数据。

没有 headroom 的话，每封装一层头都要重新分配并拷贝整个报文。有了它，一个包从驱动到应用可以做到 「分配一次、只改指针」。skb_push 还能往回推，是因为分配时就多要了空间（NET_SKB_PAD 等）。

追问：大块 payload 也存在线性区吗？—— 不。大块数据挂在 skb_shared_info.frags[]，指向 page，线性区只放头部和小段数据。这就是「零拷贝」的雏形，sendpage/MSG_SPLICE_PAGES 都走这里。

收包路径：网卡 → DMA → 中断 → NAPI → 协议栈 → socket

会问：一个包从网线到 recv() 返回，中间发生了什么？中断和轮询怎么配合？

  1. DMA 写入 RX ring。驱动预分配一组描述符（descriptor），每块指向 DMA 缓冲区。网卡收到帧后自己写内存，CPU 不参与搬运。
  2. 硬中断（top half）。中断处理只做最少的：关掉该设备的 RX 中断，调用 napi_schedule()，把 NAPI 实例挂到 per-CPU 的 poll 链表，触发 NET_RX_SOFTIRQ。
  3. NAPI poll（软中断）。net_rx_action 调驱动的 poll()，一次最多处理 weight（默认 64） 个包；整轮软中断受 netdev_budget（默认 300 包）和 netdev_budget_usecs（默认 2 ms）限制。收完才重新开中断。
  4. netif_receive_skb() 进入协议栈，按 EtherType 分发 → ip_rcv() → 路由/校验/分片重组 → tcp_v4_rcv()。
  5. TCP 层用四元组哈希找到 struct sock，把 skb 挂进 sk_receive_queue，调 sk_data_ready() 唤醒等待的进程。
  6. 用户态 recv() 被调度后 copy_to_user() 把数据拷到用户缓冲区。
NIC ──DMA──► RX ring ──IRQ──► napi_schedule()
   ──softirq NET_RX_SOFTIRQ──► poll(weight=64)
   ──► netif_receive_skb ──► ip_rcv ──► tcp_v4_rcv
   ──► sk_receive_queue ──► sk_data_ready() ──► 唤醒 recv()
为什么是「中断 + 轮询」的混合 纯中断：低 PPS 时延迟低，但高 PPS 下每包一次中断，CPU 全花在进中断上（中断风暴）。 纯轮询：高 PPS 时高效，但低 PPS 时空转。 NAPI 的做法是第一个包用中断唤醒，之后关中断批量轮询，收完再开—— 低负载像中断，高负载像轮询。

追问：多核怎么并行收包？—— 网卡多队列（RSS）按四元组哈希把连接分到不同 queue，每个 queue 配一个 CPU，用 IRQ affinity 绑定。单队列网卡只能一个 CPU 收，是高 PPS 场景的第一瓶颈。

发包路径（简述）

会问：write() 到网卡之间做了什么？TSO 省了什么？

write() 拷进 socket 发送缓冲区 → TCP 按 min(cwnd, rwnd) 取数据、加头、生成 skb → IP 查路由、必要时分片 → 邻居子系统填 MAC → 驱动 ndo_start_xmit 把描述符挂到 TX ring → 网卡 DMA 读出并发送 → 发送完成中断回收缓冲区。

TSO/GSO：内核把大块数据（最大约 64 KB）直接交给网卡，由硬件切成 MSS 大小的包， 省掉内核里的分段。驱动的 xmit_more 允许一次提交多个 skb 才敲 doorbell，减少 MMIO。

追问：为什么发包不像收包那样用 NAPI？—— 发送由应用驱动，天然有节奏；收包是外部事件驱动，才需要中断/轮询的混合。

几个「队列」，别搞混

会问：backlog 队列、accept 队列、SYN 队列、ring buffer 分别在哪？满了什么现象？

经典事故 listen(fd, 128) 而 somaxconn=4096，实际 accept 队列是 128。 突发流量下溢出，内核默认静默丢弃 ACK，客户端认为连接成功、请求却超时。 看 netstat -s | grep -i listen 的 overflow 计数。修复：listen(fd, SOMAXCONN) 并调大 somaxconn。

SO_RCVBUF 的坑：默认开启自动调优（tcp_moderate_rcvbuf=1），缓冲在 tcp_rmem[1] 和 [2] 之间按 BDP 伸缩。一旦手动 setsockopt(SO_RCVBUF)，自动调优就被关掉， 窗口固定，长肥管道下吞吐会掉。正确做法通常是只调 tcp_rmem 的上限，别动 socket 选项。

追问：怎么确认丢在哪个队列？—— ring：ethtool -S；backlog：softnet_stat 第三列；accept 溢出：netstat -s 的 listen overflows。

4 次、3 次、2 次

sendfile3（SG-DMA 时 2）2不经过用户态；数据从 page cache 直接进 socket buffer
splice / tee取决于路径2以 pipe 为中转，传的是 page 引用；tee 是复制管道内容而不消费
MSG_ZEROCOPY发送侧 0 次 CPU 拷贝2用户页 pin 住后直接 DMA；完成通知走 socket error queue

追问：为什么说 zero-copy 不是「零」？—— DMA 拷贝还在，只是不占 CPU。省掉的是「CPU 参与的拷贝」和「上下文切换」。真正的零拷贝只能让计算靠近数据（GPU/DPU）。

sendfile 与 splice

会问：写一段 sendfile 的代码？它和 splice 怎么选？

// 文件 → socket，一次系统调用
ssize_t n = sendfile(sock_fd, file_fd, &offset, count);

// 两个 fd 之间中转，必须有一端是 pipe
splice(file_fd, &off_in, pipefd[1], NULL, len, SPLICE_F_MOVE);
splice(pipefd[0], NULL, sock_fd, NULL, len, SPLICE_F_MOVE);

sendfile 适合「文件 → socket」的静态文件服务（Nginx）；splice 适合任意两个 fd 之间转发（代理）。 两者都避免数据进入用户态。如果网卡支持 SG-DMA，内核可以把 page cache 的页直接交给网卡， 连进 socket buffer 的那次拷贝都省了。

追问：sendfile 的 in_fd 能是 socket 吗？—— 不能，in_fd 必须是支持 mmap 的文件；要把 socket 数据写到文件，用 splice 或用户态中转。

DPDK 与 XDP：两种「绕过内核」

会问：两者都很快，区别是什么？

DPDKXDP
位置用户态，完全接管网卡（UIO/VFIO + PMD）内核内，驱动 NAPI poll 的最早点（分配 skb 之前）
数据路径用户态 busy-poll，无中断、无系统调用eBPF 程序返回 PASS/DROP/TX/REDIRECT
CPU独占核 100% 轮询共享，按需执行
典型场景NFV、5G UPF、高频交易DDoS 清洗、L4 负载均衡、可观测性

一句话：XDP 是「在内核里尽早处理」，DPDK 是「不要内核」。DPDK 快是因为省掉了中断、系统调用、协议栈、切换和拷贝，代价是独占 CPU 和网卡。

追问：XDP 能收包到用户态吗？—— 能，配合 AF_XDP socket，用 UMEM 做零拷贝或拷贝模式。这是 XDP 和 DPDK 之间的折中。

epoll 与 IO 多路复用

select / poll / epoll

会问：epoll 为什么快？是红黑树快吗？

selectpollepoll
fd 上限FD_SETSIZE，默认 1024无硬上限无硬上限（受 RLIMIT_NOFILE）
每次调用拷贝位图 + 遍历 O(n)拷贝数组 + 遍历 O(n)epoll_wait 只取就绪的 O(k)
内核结构无持久状态无持久状态红黑树 + 就绪链表

快的两个真正原因：① 注册只做一次（epoll_ctl），epoll_wait 不再拷贝和扫描全量 fd； ② 就绪事件由内核回调主动挂到链表，epoll_wait 只返回就绪的。 红黑树只是「fd → epitem」的索引，换成哈希表也一样快 —— 面试时能主动说这一点，比背「红黑树」高一个层次。

追问：epoll 一定比 select 快吗？—— 连接很少且都很活跃时，select 的额外开销可以忽略，epoll 的系统调用次数反而更多。epoll 赢在「连接多、活跃少」。

红黑树 + 就绪链表

会问：描述一下 epoll 的内核数据结构与事件流转。

struct eventpoll {
    struct rb_root   rbr;      // 所有注册的 fd
    struct list_head rdllist; // 已就绪的 epitem
    struct wait_queue_head wq; // 阻塞在 epoll_wait 的进程
};
  1. epoll_create 创建 eventpoll，初始化红黑树和就绪链表。
  2. epoll_ctl(ADD) 把 fd 包成 epitem 插入红黑树，并在该 fd 的等待队列上注册 ep_poll_callback。
  3. 数据到达 → 回调触发 → epitem 链入 rdllist → 唤醒 epoll_wait。
  4. epoll_wait 把 rdllist 里的事件拷到用户数组并返回。

追问：同一个 fd 同时注册在多个 epoll 实例里会怎样？—— 每个实例各有一个 epitem、各注册一次回调，事件会分别挂到各自的就绪链表。可以，但注意回调开销和复杂度。

LT vs ET：ET 必须读到 EAGAIN

会问：两者区别？ET 模式怎么写才对？为什么 ET 必须非阻塞？

  • LT（默认）：只要 fd 还有数据，每次 epoll_wait 都返回它。读不完下次还提醒，安全。
  • ET：只在状态变化时通知一次（无数据 → 有数据）。没读完就不会再收到通知。
// ET：fd 必须 O_NONBLOCK
int fl = fcntl(fd, F_GETFL);
fcntl(fd, F_SETFL, fl | O_NONBLOCK);
struct epoll_event ev = { .events = EPOLLIN | EPOLLET, .data.fd = fd };
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);

// 读循环：必须读到 EAGAIN
for (;;) {
    ssize_t n = read(fd, buf, sizeof buf);
    if (n > 0) { handle(buf, n); continue; }
    if (n == 0) { close(fd); break; }              // EOF
    if (errno == EAGAIN || errno == EWOULDBLOCK) break; // 读干净
    if (errno == EINTR) continue;
    close(fd); break;                                // 真错误
}
为什么必须非阻塞 ET 要求「一次读干净」，判断读干净的唯一办法是 read() 返回 EAGAIN。 如果 fd 是阻塞的，最后一次 read() 会挂起整个事件循环，等不到 EAGAIN。

写也一样：写缓冲满时 write() 返回 EAGAIN，要把剩余数据存进应用缓冲， 等 EPOLLOUT 再继续。ET 的正确性完全由应用负责，所以新服务优先用 LT。

追问：LT 会不会重复通知导致忙？—— 会。如果 fd 上一直有数据而你不读，epoll_wait 会一直返回。但只要你读，它就会停；这比 ET 漏读导致连接卡死容易排查得多。

惊群与 EPOLLEXCLUSIVE

会问：多个线程 epoll_wait 同一个 epfd 会怎样？怎么解决？

一个事件到来时，所有等待在同一个 eventpoll 上的进程/线程都会被唤醒，但只有一个能处理， 其余白醒一次 —— 线程越多，上下文切换浪费越大。

  • EPOLLEXCLUSIVE（4.5+）：epoll_ctl 时加上，内核只唤醒一个等待者。
  • SO_REUSEPORT：每个线程一个 epfd、各自监听同一端口，内核按四元组哈希分发连接，从根上不共享 epfd。
  • Reactor 模型：主线程 accept 后分发给 worker（Nginx / Netty 的思路）。

追问：EPOLLEXCLUSIVE 能和其他 flag 一起用吗？—— 可以和 EPOLLIN、EPOLLET 等组合；不能与 EPOLLONESHOT 同用，也不能用于 EPOLL_CTL_MOD，否则 epoll_ctl 返回 EINVAL。

RDMA 与分布式训练

为什么 RDMA 快

会问：RDMA 比 TCP 快在哪？三个特征说说。

  • Kernel bypass：ibv_post_send 在用户态直接写网卡 doorbell（mmap 的 BAR 寄存器），没有系统调用、不陷入内核。
  • Zero-copy：数据在注册过的内存（MR）和网卡之间直接 DMA，不经过内核缓冲区。
  • CPU 不参与：可靠性、重传、排序都卸载到网卡；完成事件由网卡写 CQ，用户态 ibv_poll_cq() 轮询，没有中断。

代价：需要专用网卡、无损网络、内存注册（pin 页）开销大、编程模型复杂。

追问：MR 为什么要 pin 页？—— 网卡 DMA 用的是物理地址，页被换出或迁移会导致 DMA 写到错误位置。注册时锁页并建立地址翻译表，之后网卡才能安全访问。

InfiniBand vs RoCE v2 vs iWARP

会问：RoCE v2 跑在哪？为什么要求无损网络？

InfiniBandRoCE v2iWARP
承载IB 专用链路（非以太网）以太网 + UDP/IP，端口 4791以太网 + TCP/IP
无损原生（credit-based 流控）要配 PFC / ECN不需要
现状HPC / 大模型训练主流云厂商主流，复用现网基本退出主流

RoCE 把可靠传输卸载到网卡，网卡的重传缓冲是固定的。交换机一丢包，重传风暴会放大拥塞， 所以要求 PFC 做到「不丢包」，再用 ECN 标记拥塞、让发送端降速。 RoCE 比 IB 便宜，但运维复杂度高 —— 配置出错就是性能断崖。

追问：PFC 有什么副作用？—— 可能造成「死锁」和「拥塞扩散」（pause 帧风暴），所以有 watchdog 和 PFC storm 检测。这也是云厂商推拥塞控制型无损（如 DCQCN）的原因。

verbs 编程模型：PD / MR / QP / CQ

会问：RDMA 的编程对象有哪些？一次 Send 的流程？

  • PD：保护域，QP 和 MR 必须同域才能互访。
  • MR：注册过的内存，拿到 lkey/rkey。
  • QP：一对 Send/Recv 队列，本质是环。连接 = 一对 QP。
  • CQ：完成队列，网卡写 CQE，用户轮询。
mr = ibv_reg_mr(pd, buf, size, IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE);

struct ibv_send_wr wr = {
    .opcode = IBV_WR_SEND,
    .sg_list = &sge, .num_sge = 1,
    .send_flags = IBV_SEND_SIGNALED,
};
ibv_post_send(qp, &wr, &bad_wr);   // 用户态直接写 doorbell

while (ibv_poll_cq(cq, 1, &wc) == 0) { /* spin */ }

Send/Recv 是双边：接收端必须提前 post recv。Read/Write 是单边：对方不需要参与， 只需要提供 rkey 和远端地址 —— 这是 RDMA 最强大的地方，也是内存保护必须严格的原因。

追问：为什么轮询而不是中断？—— 中断的延迟（微秒级）比 RDMA 的传输时间还大。高吞吐场景用 busy-poll，用一点 CPU 换延迟；低负载可以设 completion channel 用事件通知。

NCCL 与 Ring AllReduce

会问：Ring AllReduce 怎么走？带宽怎么算？

N 个 GPU 排成环，数据切成 N 份，两个阶段：

  1. Reduce-Scatter：走 N−1 步，每步传一份，边传边累加，结束时每个 GPU 持有其中一份的完整和。
  2. All-Gather：再走 N−1 步，把各份和广播给所有人。
S = 总数据量，N = GPU 数
每步传输     = S / N
总步数       = 2(N − 1)
每 GPU 总量  = 2(N − 1) / N × S

algbw = S / t
busbw = algbw × 2(N − 1) / N     // NCCL 报的 busbw

为什么乘这个系数：Ring 的带宽下界就是 2(N−1)/N × S。NCCL 的 busbw 定义为 「假设网络带宽被完全利用时的等效值」，所以判断是否跑满物理带宽，看 busbw，不是 algbw。

举例：8 卡、物理带宽 100 GB/s、S = 1 GB，理论最短时间 ≈ 2×7/8 × 1 GB / 100 GB/s ≈ 17.5 ms。 实测 20 ms 就是约 87% 效率。

追问：Ring 和 Tree 怎么选？—— Ring 带宽最优但步数 2(N−1)，大消息用它；Tree 是 O(log N) 步，延迟低，小消息用它。NCCL 按消息大小和拓扑自动切换。

GPUDirect RDMA 与 NVLink 的层次

会问：GPUDirect 省了什么？NVLink 和 IB 是什么关系？

普通 RDMA 是「网卡 ↔ 主存」。GPUDirect RDMA 让网卡直接 DMA 读写显存： 路径从「GPU → 主存 → 网卡」变成「GPU → 网卡」，省掉一次 PCIe 往返和一次 CPU 拷贝。 实现上由 nvidia-peermem 模块把显存页注册给网卡。

  • NVLink：单机内 GPU 之间的互连，带宽远高于 PCIe。
  • NVSwitch：把 NVLink 做成交换芯片，让机内多卡两两满带宽。
  • InfiniBand / RoCE：机器之间的网络。

大模型训练的分层很清晰：机内 AllReduce 走 NVLink/NVSwitch，跨机走 IB/RoCE + GPUDirect，数据全程不经过 CPU 主存。

追问：GPUDirect 需要什么条件？—— 支持 P2P 的 GPU、支持 GPUDirect 的网卡、正确的 PCIe 拓扑（同一 PCIe switch 或支持 ACS 转发），以及驱动模块加载。拓扑不对时性能会回退到经过主存。

高频问答

八个问题，覆盖上面 80% 的考点。建议合上页面，对着白板默写。

三次握手为什么不能两次？

两次握手时，服务端发完 SYN-ACK 就认为连接建立，无法确认客户端收到了它。SYN-ACK 丢失会让服务端单方面分配资源、客户端却在重传 SYN，双方状态不一致。

同时，两次握手下，网络里滞留的旧 SYN 可能让服务端建立一个客户端根本不知道的连接。第三次 ACK（以及随机 ISN）让客户端有机会拒绝。

四次可以，但没必要：三次已经是「双向确认」的最少次数。

追问：第三次 ACK 丢了怎么办？—— 服务端在 SYN_RCVD 会重传 SYN-ACK；客户端此时已 ESTABLISHED，收到重传的 SYN-ACK 会再回 ACK。

TIME_WAIT 有什么用？太多怎么办？CLOSE_WAIT 呢？

TIME_WAIT（2MSL = 60 s，Linux 写死）：

  • 保证最后的 ACK 能到达：ACK 丢了，对端重传 FIN，还在 TIME_WAIT 的一方可以重新 ACK。
  • 让旧连接的报文彻底消失，避免污染相同四元组的新连接。

太多：本质是短连接太多。用连接池 / keep-alive；客户端侧 tcp_tw_reuse=1（需 timestamp）；服务端 SO_REUSEADDR。不要提 tcp_tw_recycle（4.12 已移除），调 tcp_fin_timeout 也没用（它管 FIN_WAIT_2）。

CLOSE_WAIT 堆积：完全不同 —— 对端发了 FIN，本机回了 ACK，但应用没有 close()。这是连接泄漏，改代码，不是调参数。

追问：TIME_WAIT 会不会导致端口耗尽？—— 会。本机作为客户端时，主动连接用尽临时端口范围，报 Cannot assign requested address。

epoll ET 模式怎么正确读写？
  1. fd 设为 O_NONBLOCK。
  2. 读循环必须读到 EAGAIN；返回 0 是 EOF，关闭；其他错误关闭。
  3. 写循环处理 EAGAIN：剩余数据进应用缓冲，注册 EPOLLOUT，等可写再继续。
  4. 监听 EPOLLERR/EPOLLHUP，即使没注册这两个事件它们也可能被报告。

为什么必须非阻塞：判断「读干净」只能靠 EAGAIN；阻塞 fd 会挂起事件循环。

为什么 ET 容易出错：它只通知状态变化的边沿，漏读一次就永久丢事件。LT 每次 epoll_wait 都会提醒，容错性高，所以新服务优先 LT。

追问：accept 在 ET 下要注意什么？—— 也要循环 accept 直到 EAGAIN，否则并发连接会漏掉。

为什么 epoll 比 select 快？

两点，不是「红黑树」：

  1. 注册一次，不再重复拷贝和扫描。select 每次调用都要把 fd 集合拷进内核并遍历 O(n)；epoll 在 epoll_ctl 时完成注册。
  2. 就绪事件由回调挂链表。数据到达时驱动回调把 epitem 挂到 rdllist，epoll_wait 只返回就绪的 O(k)。

红黑树只是 fd → epitem 的索引，支持 O(log n) 增删查，换成哈希表也一样快。

追问：什么时候 select 更合适？—— 连接数很少且都活跃时，epoll 的额外系统调用和数据结构开销不占优；而且 select 可移植性好（跨平台）。

一次收包的完整路径？

网卡 DMA 写 RX ring → 硬中断只做 napi_schedule() → 软中断 NET_RX_SOFTIRQ 里 NAPI poll（weight 64，总预算 300 包 / 2 ms）→ netif_receive_skb → ip_rcv → tcp_v4_rcv → 四元组哈希找 socket → 挂 sk_receive_queue → sk_data_ready 唤醒进程 → copy_to_user。

三个易混队列：RX ring（网卡）、backlog（per-CPU 软中断）、socket 接收队列（每连接）。

为什么 NAPI 是混合模式：低负载用中断保证延迟，高负载关中断批量轮询避免中断风暴。

追问：多核并行靠什么？—— 网卡多队列 RSS + IRQ affinity；单队列网卡只能一个 CPU 收包。

sendfile 为什么快？拷了几次？

read+write：4 次拷贝（2 次 DMA + 2 次 CPU）、4 次上下文切换。

sendfile：3 次拷贝、2 次切换。数据在内核内部从 page cache 直接进 socket buffer，不经过用户态。若网卡支持 SG-DMA，内核把页直接交给网卡，降到 2 次拷贝。

省掉的是「内核 → 用户」的 CPU 拷贝和两次切换。

追问：零拷贝真的零吗？—— 不是，DMA 拷贝仍在，只是不占 CPU。零拷贝省的是 CPU 拷贝和上下文切换。

RDMA 为什么比 TCP 快？

① Kernel bypass：用户态直接写网卡 doorbell，无系统调用。② Zero-copy：注册内存与网卡之间直接 DMA。③ 无 CPU 参与：可靠性卸载到网卡，完成事件写 CQ，用户态轮询，无中断。

代数是：专用网卡、无损网络（RoCE 需 PFC/ECN）、MR 要 pin 页、编程模型复杂。

追问：GPUDirect 又是什么？—— 网卡直接 DMA 读写显存，绕过 CPU 和主存，跨机 NCCL 的关键。

NCCL 的 Ring AllReduce 带宽怎么算？

Reduce-Scatter + All-Gather，各 N−1 步，每步传 S/N。

每 GPU 总传输量 = 2(N−1)/N × S；algbw = S/t；busbw = algbw × 2(N−1)/N。

判断网络是否跑满，看 busbw 是否接近物理带宽。8 卡、100 GB/s、1 GB 数据，理论最短 ≈ 17.5 ms。

追问：为什么大消息用 Ring、小消息用 Tree？—— Ring 带宽最优但 2(N−1) 步；Tree 是 O(log N) 步，小消息下延迟由步数主导。
