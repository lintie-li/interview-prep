进程、线程与调度

task_struct 里有什么

Linux 不区分进程和线程的调度实体，统一是 task_struct。进程和线程的区别体现在 是否共享 mm / files / signal 等资源：clone() 的不同 flag 决定共享什么。 fork() 就是 clone(SIGCHLD, 0)，pthread_create() 底层是 clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD, ...)。

关键字段：

  • state：TASK_RUNNING / TASK_INTERRUPTIBLE / TASK_UNINTERRUPTIBLE / __TASK_STOPPED / EXIT_ZOMBIE。D 状态就是 uninterruptible，kill -9 杀不掉，通常卡在 I/O 上。
  • mm / active_mm：内核线程 mm == NULL，借用前一个进程的 active_mm，避免切换 CR3 的开销。
  • cred：权限，uid/gid + capability 位图。
  • nsproxy：namespace，容器的隔离基础。

CFS 与 EEVDF

CFS（完全公平调度）的核心是虚拟运行时间 vruntime：每颗 CPU 一个红黑树， 按 vruntime 排序，永远选最小的跑。实际执行时间按权重缩放： 优先级高的（nice 小）vruntime 增长慢，于是跑得更多。 

// 简化的核心公式
vruntime += delta_exec * (NICE_0_WEIGHT / weight)

新任务入队时，vruntime 会被设成 cfs_rq->min_vruntime， 防止它因为 vruntime 太小而霸占 CPU。这就是 sched_place_entity() 里的 place_entity() 要做的事。

2024 年之后的变化 Linux 6.6 起默认调度器换成了 EEVDF（Earliest Eligible Virtual Deadline First）， 引入了 lag 和 eligible 概念，解决 CFS 在延迟敏感任务上的公平性问题。 面试如果聊到，能说出"CFS 被 EEVDF 取代、6.6 合入"就是明显的加分。

抢占与实时

  • CONFIG_PREEMPT_NONE：服务器默认，内核态不被抢占，吞吐优先。
  • CONFIG_PREEMPT_VOLUNTARY：在 cond_resched() 处主动让出。
  • CONFIG_PREEMPT：完全可抢占，除了持锁和关中断的区域。
  • CONFIG_PREEMPT_RT：实时补丁，自旋锁变成可睡眠的 rtmutex，中断线程化，5.x 之后逐步合入主线，6.12 起完整合入。

优先级：0~99 是实时（SCHED_FIFO / SCHED_RR），100~139 是普通（SCHED_NORMAL）。 实时任务永远压过普通任务，如果实时任务死循环，可以用 sched_rt_runtime_us 给它限流（默认 95%）。

物理内存的组织

伙伴系统（buddy allocator）管页：按 2 的幂次分块，分配时找不小于需求的最小块，不够就拆大块； 释放时看伙伴是否空闲，空闲就合并。最大连续块通常是 MAX_ORDER = 11，即 4MB。

为什么会有内存碎片，怎么解决？ 伙伴系统只能合并"伙伴"，长时间运行后会出现大量不连续的空闲页，导致要一个 4MB 连续块时失败。 解法有三：① 按可迁移性给页分组（MIGRATE_MOVABLE / UNMOVABLE）， 让可迁移的页扎堆，需要时搬一搬就能凑出连续块；② CMA（Contiguous Memory Allocator） 预留一块大区域，平时给可移动页用，需要时再腾出来；③ 用 huge page 直接降低对连续性的需求。

GFP flag 是重点：GFP_KERNEL 可以睡眠（会触发回收 / IO）， GFP_ATOMIC 不能睡眠（用于中断上下文、持自旋锁时）， GFP_NOIO / GFP_NOFS 用于文件系统等会重入的场景。

页表与地址翻译

x86-64 四级页表，每级 9 位索引 + 低 12 位页内偏移。CR3 指向 PGD。 每次进程切换如果换了 mm，就要写 CR3，导致 TLB 失效 —— 这是为什么内核线程借用 active_mm（不换 CR3 就不 flush）。

TLB 失效有两个层次：invlpg 指令刷单条； PCID（Process Context ID）让 TLB 条目带进程标签，切换时不用全刷 —— Linux 里的 CR3_NOFLUSH 就是在用它。

页表项里的关键位 _PAGE_PRESENT（存在）、_PAGE_RW（可写）、_PAGE_USER（用户可访问）、 _PAGE_ACCESSED / _PAGE_DIRTY（给 LRU 和写回用）、_PAGE_NX（不可执行）。 缺页异常里 error_code 的 P/W/U/RSVD 位决定了这是不是合法访问 —— 面试问"缺页处理怎么判断是非法访问"就答这个。

缺页处理流程

  1. CPU 触发 #PF，硬件把错误码压栈，跳到 exc_page_fault。
  2. 判断地址在用户空间还是内核空间（address < TASK_SIZE_MAX）。
  3. 查 VMA（find_vma）找到地址属于哪个区域，检查权限（读/写/执行是否允许）。
  4. 分情况：匿名页 → do_anonymous_page；文件页 → do_fault 从 page cache 或磁盘读；栈增长 → expand_stack；写时复制 → do_wp_page。
  5. 分配物理页、填页表、刷 TLB、返回用户态重试那条指令。

mmap 与驱动里的 mmap

mmap 把文件或设备映射到进程地址空间。用户态调 mmap() → 内核创建 VMA → 真正访问时缺页 → 调文件系统的 fault 回调或驱动的 mmap。

驱动里实现 mmap 要做的：把设备物理地址（比如 BAR 空间）映射进用户进程。 核心是 remap_pfn_range()，或者用 vm_insert_page() 插入具体的页。 注意必须检查偏移对齐、范围、权限，否则就是提权漏洞。 

static int mydev_mmap(struct file *filp, struct vm_area_struct *vma)
{
    unsigned long pfn = __pa(bar_addr) >> PAGE_SHIFT;
    return remap_pfn_range(vma, vma->vm_start, pfn,
                           vma->vm_end - vma->vm_start, vma->vm_page_prot);
}

现代驱动更推荐 io_remap_pfn_range（用于 IO 内存）和 dma_mmap_coherent（用于一致性 DMA 内存），后者能正确处理 cache 属性。

NUMA 与内存回收

NUMA 下访问本地内存比远端快 2~3 倍。numactl --hardware 能看节点。 内核里页分配默认优先本地节点，失败才 fallback。

回收有三条路径：

  • 直接回收：分配时水位不足，同步回收（会造成延迟尖刺）。
  • kswapd：后台线程，异步回收。
  • OOM killer：实在回收不出来，按 oom_score 杀进程。

页的两种 LRU 链表（active / inactive，再分 anon / file）， 新页先进 inactive，被访问两次才提升到 active。这就是 LRU-2 的近似实现。

并发与同步

这是内核面试的核心中的核心。NVIDIA 的 JD 明确写了 "synchronization and concurrency"。

锁的选择

原语能否睡眠中断上下文适用场景
spinlock否可用（需 irqsave）短临界区，进程/软中断上下文
mutex是不可用可能长时间持锁、需要睡眠
semaphore是不可用计数型，历史遗留

为什么 spin_lock_irqsave 而不是 spin_lock_irq

// 错误：无条件开中断，会把外层关的中断也打开
spin_lock_irq(&lock);
...
spin_unlock_irq(&lock);   // 这里会开中断！

// 正确：保存原有状态，恢复时原样还原
unsigned long flags;
spin_lock_irqsave(&lock, flags);
...
spin_unlock_irqrestore(&lock, flags);

如果锁只在进程上下文用，spin_lock 就够；如果软中断也会拿这把锁， 需要 spin_lock_bh；如果硬中断也会拿，需要 spin_lock_irqsave。

RCU 原理

RCU 的核心思想：读侧零开销，写侧延迟释放。 读者在 rcu_read_lock() 和 rcu_read_unlock() 之间持有引用， 写者先移除指针（rcu_assign_pointer 更新），然后等所有读者退出临界区 （synchronize_rcu()），才真正 kfree() 旧对象。 

// 写侧
new = kmalloc(...);
copy(old, new);
rcu_assign_pointer(list->entry, new);
synchronize_rcu();     // 等所有读者离开
kfree(old);

// 读侧
rcu_read_lock();
p = rcu_dereference(list->entry);
// 使用 p，不能睡眠
rcu_read_unlock();
grace period 为什么能确定读者退出 经典 RCU 依赖 静止态（quiescent state）：CPU 发生上下文切换、用户态执行、 或进入 idle，都说明它肯定不在 RCU 读临界区里了。所以只要所有 CPU 都经过一次静止态， 就说明没有老读者了。这也是为什么 RCU 读侧不能睡眠 —— 睡眠会导致上下文切换， 而读者还没用完对象。

内存屏障与原子操作

三种屏障：

  • barrier()：编译器屏障，只阻止编译器重排。
  • smp_mb()：全屏障，阻止 CPU 重排。
  • smp_rmb() / smp_wmb()：读/写屏障。
  • smp_read_barrier_depends()：数据依赖屏障，在 Alpha / 弱一致性架构上需要。

经典用法是无锁队列 / 环形缓冲区。比如生产者在写满数据之后才更新 tail， 消费者看到 tail 变化才能读数据 —— 这中间需要 smp_wmb()。 

// 单生产者单消费者环形队列
// 生产者
buf[tail % N] = data;
smp_wmb();                    // 确保数据先写入，再更新 tail
WRITE_ONCE(tail, tail + 1);

// 消费者
if (READ_ONCE(tail) == head) return EMPTY;
smp_rmb();
data = buf[head % N];
head++;

中断、软中断与下半部

上半部与下半部

中断处理要尽可能快，因为关中断期间系统失去响应。所以拆成两半：

  • 上半部（hardirq）：关中断执行，只做最紧急的事 —— 读状态、清中断标志、唤醒下半部。不能睡眠。
  • 下半部：稍后执行，做耗时工作。有三种机制：
    • softirq：静态注册，同一类可以在多 CPU 并行，用于网络、块设备、定时器。
    • tasklet：基于 softirq，同一 tasklet 串行执行，适合驱动。新代码不太推荐了。
    • workqueue：在进程上下文执行，可以睡眠，最灵活。
选哪个？ 需要睡眠（拿 mutex、做 IO）→ workqueue。 不需要睡眠且要求低延迟 → tasklet。 内核基础设施（网络、块）→ softirq。 现代驱动基本都用 workqueue 或 threaded irq（request_threaded_irq）。

中断处理的完整路径

  1. 硬件发中断 → CPU 查 IDT → 跳到 common_interrupt。
  2. irq_enter() 更新统计，generic_handle_irq() 找到中断控制器对应的 irq_desc。
  3. 调 irq_desc->handle_irq（比如 handle_edge_irq），它会调注册的 handler。
  4. handler 返回 IRQ_WAKE_THREAD 则唤醒 threaded handler。
  5. irq_exit() 里检查是否有待处理的 softirq，有就 __do_softirq()。

中断亲和性

/proc/irq/<n>/smp_affinity 设置某个中断由哪些 CPU 处理。 高性能场景要把网卡中断绑到与业务进程同 NUMA 节点的 CPU 上，避免跨节点访问。 irqbalance 会自动做这件事，但有时会帮倒忙。

设备驱动模型

总线 / 设备 / 驱动

Linux 2.6 之后统一成 bus_type / device / device_driver 三件套。 probe 的触发流程：设备注册 → 总线遍历驱动看是否 match → 匹配上就调 probe()。 

struct platform_driver mydrv = {
    .probe  = my_probe,       // 匹配上了，初始化硬件
    .remove = my_remove,      // 卸载或设备移除
    .driver = {
        .name = "mydev",
        .of_match_table = my_of_match,   // 设备树匹配

// 老式：通过 name 字符串匹配

字符设备

三件套：alloc_chrdev_region → cdev_init → cdev_add。

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .release = my_release,
    .read    = my_read,
    .write   = my_write,
    .unlocked_ioctl = my_ioctl,
    .mmap    = my_mmap,
    .poll    = my_poll,
};

ioctl 设计要点：用 _IO / _IOR / _IOW / _IOWR 宏生成命令号，把方向、大小、类型编码进去，这样内核能在 copy_from_user 前校验长度。 不要自定义裸整数命令号，容易和别人冲突。

read/write 返回值的坑：返回实际字节数；返回 0 表示 EOF； 返回 -EFAULT 表示用户地址非法；-EAGAIN 表示非阻塞下无数据（要配合 poll 用）。 短读短写是合法的，用户态要循环。

poll / epoll 支持

static unsigned int my_poll(struct file *f, poll_table *wait)
{
    struct my_dev *dev = f->private_data;
    unsigned int mask = 0;

    poll_wait(f, &dev->readq, wait);   // 注册等待队列
    if (has_data(dev)) mask |= POLLIN | POLLRDNORM;
    if (can_write(dev)) mask |= POLLOUT | POLLWRNORM;
    return mask;
}

注意 poll_wait 只是注册回调，不阻塞。epoll 的 ET 模式下， 必须把数据读到 -EAGAIN 才返回，否则不会再触发。

DMA

两种映射：

  • 一致性映射（dma_alloc_coherent）：CPU 和设备看到的内存一致，硬件维护 cache 一致性。适合长期存在、频繁访问的缓冲区。可能分配在非缓存区，访问慢。
  • 流式映射（dma_map_single / dma_map_sg）：每次传输前映射，传输后 dma_unmap_single。适合单次传输。

关键点：设备看到的是总线地址（dma_addr_t），不是物理地址。 有 IOMMU 时两者完全不同，必须用 virt_to_phys 会错。正确做法是用 dma_map_* 系列接口。

常见 bug kmalloc 分配的缓冲区如果超过 cache line 且和其他数据共享 cache line， dma_sync_single_for_cpu/device 会破坏相邻数据（false sharing）。 大缓冲区要按 cache line 对齐（____cacheline_aligned）。

sysfs / procfs / debugfs

  • sysfs：/sys，展示设备树、驱动、总线的层次结构，每种 kobject 一个目录。属性用 DEVICE_ATTR 宏定义。
  • procfs：/proc，进程信息和内核状态，新代码不推荐加东西。
  • debugfs：/sys/kernel/debug，专门调试用，可以读写任意数据，没有 ABI 稳定性承诺。

文件系统与 IO

VFS 四件套

super_block / inode / dentry / file。

  • super_block：一个挂载的文件系统实例。
  • inode：一个文件（元数据），文件系统相关。
  • dentry：目录项，路径的一次解析结果，有 dcache 缓存。
  • file：打开的文件描述，包含偏移量和操作表。

一个 inode 可以有多个 dentry（硬链接），一个文件可以被多次 open 得到多个 file 结构。 这就是 unlink 之后文件还在的原因 —— inode 的引用计数还没到 0。

page cache 与 writeback

读文件先查 page cache，没有才读磁盘。写文件默认是 write-back：先写 cache， 标记 dirty，由内核线程 kworker 按 dirty_ratio 刷盘。 fsync() 强制刷盘并等完成，fdatasync() 只刷数据不刷元数据。

为什么数据库都要 fsync 因为 write() 返回成功只代表写进了 page cache，断电就丢了。 所以数据库的 WAL 机制每一步都要 fsync（或用 O_DIRECT 绕过 cache）。 这也是为什么 O_DIRECT 在小 IO 上反而慢 —— 没有 cache 合并。

IO 调度

mq-deadline（默认，保证截止时间）、bfq（桌面，公平性）、kyber（快速设备）。 对于 NVMe 这类高性能设备，调度开销可能大于收益，可以直接用 none。

高频问答

进程、线程、协程在内核层面有什么区别？

内核只认 task_struct。进程和线程的区别是资源共享：进程有独立的 mm、文件表、信号处理； 线程共享这些。协程完全是用户态概念，内核看不见，一个协程对应多个用户态栈帧， 由语言运行时调度到 OS 线程上。

关键点：线程切换要陷入内核（或至少切栈），协程切换纯用户态，所以协程切换成本是纳秒级， 线程是微秒级。io_uring 和 epoll 让 IO 不需要线程阻塞等待， 这是现代高并发服务的基础。

一个 malloc 之后，从用户态到物理内存，中间发生了什么？

① malloc 小于 128KB 时走 brk 堆，直接移动 program break； 大于 128KB 走 mmap 建立匿名映射。

② 此时只是建立了 VMA，还没有分配物理页（延迟分配 / overcommit）。

③ 第一次访问触发缺页异常 → 内核分配物理页 → 填页表 → 刷 TLB。

④ 如果系统内存紧张，页可能被换出到 swap，访问时再换回来。

追问：malloc(0) 返回什么？合法实现可以返回 NULL 或一个可 free 的指针， glibc 返回一个最小块。free 之后内存去哪了？小的进 tcache / fastbin，不一定还给 OS。

写时复制（COW）的完整流程

fork() 时不复制页表，父子共享物理页，页表项都设成只读，引用计数 +1。

任何一方写 → 触发写保护缺页（do_wp_page）→ 分配新页 → 复制内容 → 改为可写。

优化点：fork() 时如果页是只读的（比如代码段），可以永久共享，不用写时复制。

面试常问：为什么 fork() 之后子进程调用 exec() 会浪费？ 因为复制了一堆马上要丢弃的页。所以有 vfork() 和 posix_spawn， 以及 Linux 的 clone(CLONE_VM)。

自旋锁和互斥锁，什么时候用哪个？

自旋锁：临界区极短（几个指令），且不能睡眠，用于中断上下文。 自旋期间浪费 CPU，所以临界区必须短。

互斥锁：可能长时间持有，允许睡眠。睡眠时让出 CPU，适合可能阻塞的操作（IO、大块内存分配）。

选错会死锁：中断上下文里用 mutex_lock 直接 BUG（might_sleep 检查会报）。 进程上下文里持有自旋锁去 kmalloc(GFP_KERNEL) 也是 BUG。

进阶：优先用 lockless 设计（RCU、原子操作、per-CPU 变量），能不锁就不锁。

如何实现一个高性能的无锁环形缓冲区？

单生产者单消费者最简单：head / tail 两个原子变量， 生产者只改 tail，消费者只改 head，用 smp_wmb / smp_rmb 保证顺序， 不需要 CAS。

多生产者需要 CAS 循环更新 tail；或者用 lwsync 之类的屏障组合。 更常见的是用 per-CPU 队列避免竞争，或者用 io_uring 那种共享内存 + 原子索引的方案。

关键点：ABA 问题（值改回原样导致 CAS 误判）、伪共享（head/tail 在同一 cache line 上， 需要 padding 到 64 字节对齐）。

内核 panic 了怎么定位？

① 看 dmesg / 串口日志，找 RIP 指向哪行代码、Call Trace 调用栈。

② 有 vmcore 的话用 crash 分析（crash vmlinux vmcore）， 可以看寄存器、栈、内存、任务列表。

③ Oops 之外还有 BUG_ON / WARN_ON 的区别： WARN 只打印不挂，BUG 直接 die。

④ 偶发的可以用 kdump / kexec 保留现场，用 pstore 存到 NVRAM。

⑤ 竞态类问题用 KCSAN（内核并发检查器），内存越界用 KASAN，也都能用 syzkaller 做模糊测试。

用户态和内核态之间怎么高效传输数据？

传统是 copy_to_user，两次拷贝（用户→内核→设备），有开销。

零拷贝方案：

  • mmap 设备内存或 DMA 缓冲区到用户态，双方直接访问。
  • 共享内存 + 无锁队列（io_uring 就是这种，内核和用户共享 ring buffer）。
  • 大块传输用 DMA scatter-gather，避免 CPU 参与。

GPU 驱动的 UMD/KMD 分层就是这个思路：UMD 直接在用户态填命令缓冲区， 通过共享内存提交给硬件，只有需要内核介入时才 ioctl。

怎么保证驱动代码在 SMP 下是正确的？

① 明确数据的所有权和访问上下文：哪些数据只在进程上下文访问，哪些会被中断访问。 画出锁的层次图，避免锁顺序反转。

② 用 lockdep：CONFIG_PROVE_LOCKING 能检测锁顺序反转、死锁、缺失解锁。

③ 用 KCSAN 检测数据竞争。

④ 用 smatch / sparse 静态检查。

⑤ 压力测试：并发 + 注入延迟 + CPU 热插拔 + 内存压力同时来。

⑥ 代码审查：每一处共享变量都要能说出"谁写、谁读、用什么保护"。
