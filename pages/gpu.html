GPU 软件栈与 CUDA

这一页的主角是 软件怎么驾驭 GPU，不是怎么写 kernel。 做过用户态驱动的同学，这里的 UMD/KMD 分界、命令提交、内存管理、同步机制， 应该有一半是每天在打交道的 —— 面试要做的就是把经验翻译成对方听得懂的语言。

先划清边界 不考算子：不写 __global__ kernel，不做 shared memory 优化，不调 tile size。 考的是：CUDA 上下文怎么建立、命令怎么提交到硬件、显存怎么分配和迁移、 流和事件的同步语义是什么、多进程多卡怎么协调。 "软件怎么把工作交给硬件并保证正确" —— 这就是驱动岗的视角。

GPU 架构：为什么它快

CPU 用大量面积做缓存和乱序控制，追求单线程延迟； GPU 把面积几乎全给了 ALU，用海量线程和延迟隐藏换吞吐。 这个区别决定了整个软件栈的设计。

维度CPUGPU
核心数几十个几千到上万个
单核复杂度乱序、分支预测、大 cache顺序、简单、小 cache
优化目标降低延迟提高吞吐
内存DDR，几 TB/s 级（多通道）HBM，几 TB/s

SM 与 warp：执行的基本单位

NVIDIA 的层次是 Grid → Block → Warp → Thread。 硬件上，一个 SM（Streaming Multiprocessor）有若干 warp scheduler， 每个调度器管一个 warp（32 个线程），以 warp 为单位发射指令 —— 这叫作 SIMT。

  • 一个 block 被调度到一个 SM 上，block 内的 warp 分给 SM 的各个 scheduler。
  • warp 内 32 个线程如果走不同分支，会串行执行两个分支（分支发散）。
  • 占用率（occupancy） = 活跃 warp 数 / 硬件上限，受寄存器、shared memory、block 大小限制。
  • 一个 warp 的指令延迟靠切换到其他 warp 来隐藏 —— 所以 warp 越多越好（但受资源限制）。
为什么共享内存是按 block 分配的 shared memory 是 SM 上的片上资源，只有同一个 block 内的线程能共享， 因为 block 保证在同一个 SM 上执行。不同 block 之间不能共享 shared memory， 这是硬件决定的，不是软件限制。

注意 HBM 是堆叠在封装里的，位宽可以做到 4096 bit 甚至更宽， 这是它带宽远高于 DDR 的根本原因。带宽 = 位宽 × 频率，位宽是硬件决定的。

软件栈分层

这是最关键的一节。把所有东西按层摆清楚：

┌─────────────────────────────────────────┐
│  应用：PyTorch / TensorFlow / 自定义程序    │
├─────────────────────────────────────────┤
│  运行时：CUDA Runtime (libcudart)         │  ← cudaMalloc / cudaMemcpy / <<<>>>
├─────────────────────────────────────────┤
│  驱动 API：CUDA Driver (libcuda)          │  ← cuCtxCreate / cuLaunchKernel
├─────────────────────────────────────────┤
│  用户态驱动 UMD：CUDA UMD                  │  ← 编译成 GPU ISA、填命令缓冲区
├─────────────────────────────────────────┤
│  内核态驱动 KMD：nvidia.ko                 │  ← 分配显存、中断、上下文切换
├─────────────────────────────────────────┤
│  硬件：GPU / GSP 固件 / 命令处理器           │
└─────────────────────────────────────────┘

严格的边界是 UMD / KMD：UMD 在用户态，能直接读写映射进来的显存和 命令缓冲区（MMIO 或 BAR 映射），所以提交一个 kernel 的常规路径不需要系统调用； KMD 只在需要内核权限时介入 —— 分配新显存、建立地址映射、处理缺页、切换上下文。

Runtime API vs Driver API

维度Runtime API（libcudart）Driver API（libcuda）
前缀cuda*（cudaMalloc）cu*（cuMemAlloc）
上下文隐式管理，第一次调用自动创建显式 cuCtxCreate

Runtime API 是 Driver API 的一层封装。比如 cudaMalloc 背后是 cuMemAlloc，加上隐式上下文管理和错误检查。 深度学习框架（PyTorch）最终走的都是 Driver API。

UMD / KMD 分工（重点）

职责UMD（用户态）KMD（内核态）

面试可以主动讲这个 可以这样答："UMD 层典型的路径是用户态直接填命令队列， 通过 doorbell 寄存器通知硬件，只有创建上下文、分配新显存、处理异常这类 需要内核权限的操作才走 ioctl。" —— 这一句话就证明你懂 为什么 GPU 驱动要分两层。

上下文、模块与流

CUDA Context

一个 CPU 进程对应至少一个 CUDA context，context 是所有 GPU 资源的容器： 显存分配、模块、流、事件都挂在某个 context 下。切换 context 是重量级操作 —— 需要保存/恢复整个 GPU 状态（寄存器、页表基址、缓存），成本在几十微秒到毫秒。

两个特殊上下文：

  • Primary context：每个设备每个进程一个，Runtime API 默认用这个。
  • Custom context：用 Driver API 显式创建，可以有多个，用于精细控制。
context 切换为什么贵 因为 GPU 是"整卡"资源。不同 context 有不同的虚拟地址空间、不同的页表， 切换时要把 TLB 刷掉、把硬件状态存到显存、把新状态加载回来。 这也是为什么多进程共享 GPU 效率低、MPS 和 MIG 存在的意义。

Stream 与执行顺序

一个 stream 是一个有序队列：submit 到同一个 stream 的操作严格按顺序执行； 不同 stream 之间没有顺序保证，可以并发（如果资源允许）。 

cudaStream_t s1, s2;
cudaStreamCreate(&s1);
cudaStreamCreate(&s2);

kernelA<<<grid, block, 0, s1>>>();   // 和 B 可以并发
kernelB<<<grid, block, 0, s2>>>();
kernelC<<<grid, block, 0, s1>>>();   // 一定在 A 之后

cudaDeviceSynchronize();              // 等所有 stream

默认流（legacy default stream）很特殊：它会和所有其他 stream 同步 —— 也就是说 legacy default stream 里的操作会等所有 stream 完成，也会阻塞所有 stream。 这常常是性能杀手。所以有了 --default-stream per-thread 编译选项和 cudaStreamNonBlocking。

Event 与同步

Event 是轻量级的同步点，插在 stream 里，可以：

  • cudaEventRecord：在 stream 当前位置打一个标记。
  • cudaEventSynchronize：CPU 阻塞等这个标记被 GPU 处理完。
  • cudaStreamWaitEvent：让另一个 stream 等这个 event（跨 stream 同步，不需要 CPU 介入）。
  • cudaEventElapsedTime：测量两个 event 之间的 GPU 时间。
// 跨 stream 同步的典型用法：s2 等 s1 完成
cudaEventRecord(ev, s1);
cudaStreamWaitEvent(s2, ev, 0);
// 现在 s2 中后续操作一定在 s1 的 ev 之前所有操作之后

CUDA Graphs

NVIDIA 的 Principal JD 里明确提到了 CUDA Graphs。它的动机是： launch 开销。每次 <<<>>> 都要走一遍运行时 → 驱动 → 硬件， 小 kernel 密集的场景，launch 开销能占到总时间的 50% 以上。

CUDA Graph 把一串操作录制成图，之后一次性提交整个图，硬件按依赖关系调度， 把 N 次 launch 合并成 1 次。对于推理这类固定的计算图，收益非常明显。 

// 1. 录制
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
launchA(); launchB(); launchC();
cudaStreamEndCapture(stream, &graph);

// 2. 实例化（只做一次）
cudaGraphInstantiate(&exec, graph, NULL, NULL, 0);

// 3. 每次循环只需一次 launch
for (int i = 0; i < N; i++)
    cudaGraphLaunch(exec, stream);
Graph 在驱动层是怎么实现的 图被上传到 GPU 一次，硬件里有专门的图调度器，节点之间的依赖由硬件解析、 不需要 CPU 逐个 launch。这也是为什么它能把 launch 开销从微秒降到纳秒级。 面试如果问"CUDA Graphs 为什么快"，答案就是把 CPU 侧的重复工作搬到了硬件侧。

显存管理与统一内存

分配方式

API说明特点
cudaMalloc常规分配同步，慢，会阻塞
cudaMallocAsync流序分配器（11.2+）异步，基于内存池，避免全局同步
cudaMallocManaged统一内存CPU/GPU 都能直接访问，自动迁移
cudaHostAlloc锁页主机内存（pinned）DMA 必需，不能换出
cudaMemcpyAsync异步拷贝配合 stream 和 pinned 内存才能真异步
最常见的性能 bug cudaMemcpy 用普通 malloc 的内存，驱动必须先把数据拷到内部 pinned buffer， 再 DMA 到 GPU —— 变成同步的、双倍拷贝。 正确做法：cudaHostAlloc 分配 pinned 内存 + cudaMemcpyAsync + stream。 这是"为什么我的异步不异步"的标准答案。

Unified Memory 与 HMM

统一内存的目标是让程序员不用手动 memcpy。CPU 和 GPU 共享同一个虚拟地址， 物理页可以在两边迁移。实现上依赖 GPU 缺页机制：

  1. GPU 访问一个不在显存里的页 → 触发 GPU 缺页异常。
  2. KMD 处理异常，找到对应的主机内存页。
  3. 把页迁移到显存（或者建立映射，如果硬件支持直接访问主机内存）。
  4. 更新 GPU 页表，恢复执行。

Linux 上的 HMM（Heterogeneous Memory Management）是把这个能力做进内核主体： 用 migrate_vma 系列接口让设备驱动能安全地迁移进程的匿名页， 用 mmu_interval_notifier 在 CPU 侧页表变化时通知设备驱动。 NVIDIA 的 nvidia.ko 就是这么接的。

统一内存的代价 第一次访问一个页会触发缺页，延迟是毫秒级。如果页在 CPU 和 GPU 之间反复迁移 （thrashing），性能会比手动拷贝差得多。 所以有 cudaMemAdvise 告诉驱动"这个页固定放哪"、 cudaMemPrefetchAsync 主动预热。

GPU 页表与地址翻译

GPU 有自己的 MMU，自己的页表。cudaMalloc 返回的地址是GPU 虚拟地址， 和 CPU 虚拟地址是两套。驱动负责建立映射。

在虚拟化里更复杂：guest 的 GPU 虚拟地址 → guest 的 GPU 物理地址 → host 的物理地址， 需要 GPU 侧的 IOMMU（如 NVIDIA 的 ATS / SMMU）来做第二级翻译。 这是 vGPU 和 GPU 直通的核心难点。

命令提交与调度

Ring Buffer 模型

GPU 驱动的通用模型：用户态在环形缓冲区里填命令（command buffer / pushbuffer）， 然后更新 tail 指针（写 doorbell 寄存器），硬件从 head 开始消费。 

// 用户态填充，只有最后写 doorbell 才涉及硬件
cmd = ring->buf + ring->tail % ring->size;
cmd->op    = CMD_DISPATCH;
cmd->addr  = kernel_gpu_addr;
cmd->grid  = dim3(64, 1, 1);
cmd->block = dim3(256, 1, 1);
ring->tail++;

/* 内存屏障，确保命令写完 */
wmb();
/* 通知硬件：写 doorbell */
*ring->doorbell = ring->tail;

这套模型的优点是：常规提交路径没有系统调用，用户态直接写内存和 MMIO， 延迟极低（几十纳秒）。代价是没有隔离 —— 密码就在 UMD 里，所以 UMD 的 bug 就是安全漏洞。

GPU 侧调度

提交上去的 kernel 不会立刻执行，而是进到 GPU 的调度器里排队。 不同厂商的实现不同：

厂商调度部件特点
NVIDIAGigaThread Engine + 硬件调度器负责把 block 分发到各个 SM
AMDMEC / MES（Micro Engine Scheduler）固件实现的调度器，无需 CPU 参与
QualcommRingbuffer + 固件 dispatch移动端更轻量

重点理解：CPU 提交和 GPU 执行是异步的、解耦的。 CPU 提交 100 个 kernel 可能只用 100 微秒，GPU 执行要 100 毫秒。 这也是为什么需要一个足够深的硬件队列 —— 队列浅了，CPU 会饿死 GPU。

调度策略涉及：时间片（多个 context 抢同一张卡时）、 优先级（stream 优先级）、抢占（现代 GPU 支持指令级抢占， 但代价高，通常只在 kernel 边界抢占）。

同步与内存一致性

主机与设备的同步

  • cudaDeviceSynchronize()：等所有 stream，最重。
  • cudaStreamSynchronize(s)：等一个 stream。
  • cudaEventSynchronize(e)：等一个 event，最轻。
  • cudaStreamQuery(s)：非阻塞查询，返回 cudaSuccess 或 cudaErrorNotReady。
隐式同步是性能杀手 很多 API 会隐式 cudaDeviceSynchronize： cudaMalloc（旧版）、cudaMemcpy（同步版）、 cudaFree、以及访问 host 侧的 cudaMemcpy 结果。 在 profile 里看到 "GPU 有空隙"，先查是不是有隐式同步。

CUDA 内存模型与一致性

JD 里两次提到 "memory coherence and consistency models"。 CUDA 的内存模型比 C++ 弱，需要显式 Fence：

  • __syncthreads()：block 内所有线程到达屏障，且能看到彼此在 shared memory 的写。这是 block 级。
  • __threadfence()：当前线程的所有写在 device 范围内可见之前，后续访问不会重排。这是 device 级。
  • __threadfence_system()：扩展到 host 可见。
  • 原子操作：atomicAdd 等，默认 device 范围，_system 后缀扩展到 host。

在 Volta 之后，CUDA 引入了更细粒度的 acquire/release 语义 （cuda::atomic、cuda::std::atomic），和 C++11 内存模型对齐。 老代码靠 volatile + __threadfence，新代码推荐用 cuda::atomic。

一个经典问题 "为什么 GPU 上不能直接用 C++ 的 std::atomic？" 答：因为 GPU 线程模型和 CPU 不同 —— 没有抢占式调度、warp 内线程同步执行、 memory scope 分 block/device/system 三级。CUDA 提供了带 scope 参数的原子操作， 语义更精确，性能也更好。

PCIe 与主机侧的可见性

PCIe 是posted write：写操作先进入发送队列，CPU 不等确认就继续。 所以写完一个数据后，要让 GPU 看到，需要：

  1. 保证数据已经离开 CPU 的写缓冲（sfence 或 wmb()）。
  2. 保证 PCIe 事务已经被 GPU 收到（可能需要读回一个寄存器做 flush）。

这就是为什么 cudaMemcpyAsync + pinned memory 才能真异步 —— 驱动知道这块内存不能被换出、地址稳定，可以直接 DMA。

多进程、多卡与拓扑

MPS（Multi-Process Service）

默认情况下，多个进程不能同时用同一张卡（context 切换开销大）。 MPS 让多个进程共享同一个 context，由 MPS server 统一提交， 避免 context 切换，也允许多个进程的 kernel 并发执行。

限制：MPS 下没有进程间隔离（一个进程崩溃可能影响其他），共享同一个显存池。

MIG（Multi-Instance GPU）

A100 之后引入。把一张物理 GPU 硬切成多个独立实例， 每个实例有自己的 SM、显存、L2 slice、带宽。这是硬件级隔离， 每个实例就像一个独立的小 GPU。

MPSMIG
隔离级别软件（共享 context）硬件（独立 SM/显存）
故障隔离无有
显存共享，可超分物理切分
适用多用户共享、小任务多租户、云服务

NVLink 与拓扑

多卡之间通信走 PCIe 还是 NVLink，带宽差一个数量级：

互连带宽（单向）说明
PCIe 4.0 x16~32 GB/s通用
PCIe 5.0 x16~64 GB/s新平台
NVLink 3（A100）~300 GB/s专用，卡间直连
NVLink 4（H100）~450 GB/s配合 NVSwitch 全互联

nvidia-smi topo -m 能看到拓扑矩阵：NV# 表示走 NVLink， PIX/PXB 表示同一个 PCIe switch，SYS 表示跨 NUMA 节点。 分布式训练时要让通信量大的 rank 走 NVLink 或同一 switch。

高频问答

为什么 GPU 驱动要分用户态和内核态两层？

性能：命令提交如果每次都走系统调用，开销太大。UMD 直接写映射进用户态的 命令缓冲区，一次 launch 只需几十纳秒；如果走 ioctl，每次至少几微秒。

安全：真正的危险操作 —— 分配显存、改页表、访问硬件寄存器 —— 必须有内核把关， 否则一个用户进程就能破坏其他进程甚至整机。

抽象：KMD 提供最小可用的能力（alloc、map、submit、wait）， UMD 在此之上实现完整的 API（CUDA / Vulkan / OpenCL）。同一个 KMD 可以支撑多个 API。

这就是 DRM 的子系统的设计哲学，也是 NVIDIA 从闭源 nvidia.ko 分出一个 很小的 nvidia-drm.ko 接进标准 DRM 框架的原因。

一次 kernel launch 从 API 调用到硬件执行，经历了什么？
  1. kernel<<<>>>() → Runtime 检查上下文、参数、错误。
  2. Runtime 把参数打包成驱动期望的格式，调用 Driver API（cuLaunchKernel）。
  3. UMD 把命令写进命令缓冲区，写入 kernel 的 GPU 虚拟地址、grid/block 维度、参数地址。
  4. UMD 更新 ring buffer 的 tail，写 doorbell 寄存器通知硬件。
  5. GPU 的 front-end 解析命令，把 block 分发到 SM（GigaThread Engine）。
  6. SM 里的 warp scheduler 依次发射线程执行。
  7. 执行完，GPU 写完成信号，触发中断（或被 poll 到），KMD 唤醒等待者。

追问：如果 kernel 参数很大（超过 4KB），怎么办？驱动会把它放到一个特殊的 constant bank， 或者从显存里的一个 buffer 读，而不是塞进命令缓冲区。

cudaMalloc 为什么慢？怎么优化？

cudaMalloc 慢的原因：① 它是同步的，会等待所有正在进行的操作完成； ② 每次都要向 KMD 请求新的显存、建立 GPU 页表项；③ 可能有碎片整理。

优化：

  • 内存池：一次大块分配，自己管理。PyTorch 的 caching allocator 就是这个思路。
  • cudaMallocAsync：流序分配器，基于内存池，异步，不会全局同步。
  • 避免在热路径里分配/释放，预分配 + 复用。

面试常追问：PyTorch 的显存碎片是怎么产生的？因为不同大小的 tensor 交错分配释放， 大块空闲但被小 tensor 占用而无法合并。

Stream 和 Event 的关系？如何实现跨 stream 同步？

Stream 是执行队列，Event 是队列中的标记。

跨 stream 同步：cudaEventRecord(ev, s1) 在 s1 中打点， cudaStreamWaitEvent(s2, ev, 0) 让 s2 等待。整个过程不需要 CPU 介入， 是 GPU 侧的同步。

对比：cudaStreamSynchronize 是 CPU 等待，会让 CPU 阻塞； Event 可以在不阻塞 CPU 的情况下建立依赖。

典型场景：多 stream 流水线 —— s1 做数据预处理，s2 做计算， 用 event 让 s2 等 s1 的每一批数据，实现流水并行。

统一内存（Unified Memory）的优缺点？什么场景不该用？

优点：编程简单，不用手动 memcpy；支持超分配（申请超过显存的量）； 支持 GPU 直接访问主机内存（zero-copy）。

缺点：

  • 首次访问缺页，延迟高。
  • 页迁移开销大，thrashing 时性能极差。
  • 实现依赖 GPU 硬件支持（页错误处理），老的 GPU 不支持精细粒度。

不该用的场景：数据量固定且能预知、追求极致性能的训练场景 —— 手动 cudaMemcpyAsync + pinned memory 更快更可控。 统一内存更适合数据量动态、开发效率优先的场景，比如原型开发和某些推理场景。

GPU 缺页异常和 CPU 缺页异常有什么区别？

CPU：页错误由 MMU 触发，内核的 do_page_fault 处理， 进程被挂起，处理完恢复。

GPU：页错误由 GPU 的 MMU 触发，通过中断通知 KMD， KMD 查页表、找对应主机页、迁移到显存、更新 GPU 页表，然后恢复 GPU 执行。

难点：① GPU 有大量并发线程，一个缺页可能阻塞整个 warp； ② 缺页处理涉及 GPU 和 CPU 两个页表，要保证一致性； ③ 在虚拟化环境下还有第三层翻译。

NVIDIA 的 HMM + mmu_interval_notifier 就是解决这个问题的 内核机制：当 CPU 侧页表变化（比如页被换出），通知 GPU 驱动，驱动再更新 GPU 侧映射。

讲讲你遇到过的最复杂的驱动问题

这是 STAR 题，但驱动岗有特定的加分点：

  • 强调时序问题：不是逻辑错，是并发下的竞态。比如"多线程同时提交，命令缓冲区指针错乱"。
  • 强调定位手段：怎么发现的？用什么工具？dmesg、ftrace、硬件计数器、还是自己加 trace？
  • 强调验证：修完怎么证明修对了？跑了多少轮压力测试？有没有用 KCSAN / TSAN？
  • 强调影响：这个问题影响了什么？修完提升了多少？

不要讲"我实现了 XX 功能"，要讲"我定位并解决了一个 XX 问题"—— 资深岗看的是解决未知问题的能力，不是执行已知需求的能力。
