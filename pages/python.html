Python

这个方向 Python 是工具链和胶水层，不是主业。面试官问 Python，真正想确认的就四件事： 懂不懂 GIL、懂不懂对象与引用的语义、 懂不懂生成器的状态、以及明不明白为什么 GPU 框架的核心必须写 C++。

这一页的边界 只讲会被追问的部分。装环境、列表推导、pytest 用法这些不写 —— 那些是“会用”， 面试考的是“知道运行时在干什么”。下面每个小节都按 会问什么 → 精准答案 → 追问链 组织。

对象模型与引用语义

一切皆 PyObject

面试官会问：Python 的对象在内存里长什么样？变量存的是什么？

CPython 里所有值都是 PyObject 的实例，变量只是指向对象的指针。 对象头部固定两个字段： 

typedef struct _object {
    Py_ssize_t    ob_refcnt;  /* 引用计数 */
    PyTypeObject *ob_type;    /* 指向类型对象 */
} PyObject;

64 位下头部就是 16 字节。int 是 PyLongObject（头部 + 变长 digit 数组）， 不是机器字 —— 这既解释了任意精度整数，也解释了为什么 Python 的算术慢： 每次运算都可能分配新对象，并且要先查 ob_type 找到 __add__。

追问：那 PyObject 和 PyVarObject 什么关系？（后者多一个长度字段，用于 list/str 这类变长对象。）

is、== 与缓存陷阱

面试官会问：is 和 == 的区别？a = 1000; b = 1000; a is b 是什么结果？

is 比较对象身份（CPython 里是 id()，即地址）， == 调用 __eq__ 比较值。id() 是 CPython 实现细节，语言层面只保证对象存活期间唯一。

  • 小整数缓存：-5 ~ 256 在解释器启动时预创建，复用同一对象，所以 a is b 为 True。
  • 字符串驻留：像标识符的字符串、以及同一 code object 内的编译期常量会共享对象；运行时可 sys.intern() 手动驻留。
  • 超出范围的整数，结果取决于是否被常量折叠、是否同一个 code object —— 不可依赖。
正确用法 is 只用于 None、True/False、以及自己造的哨兵（_MISSING = object()）。 其余一律用 ==。写 if x is None，不要写 if x == None。

追问：缓存的边界在哪？（CPython 预创建 -5 ~ 256，超出范围的对象不会自动复用；同一 code object 内的字面量还会被常量折叠合并 —— 这两点都属实现细节。）

引用计数与循环 GC

面试官会问：Python 怎么回收内存？循环引用怎么处理？

以引用计数为主：赋值、传参、入容器 +1，重新绑定、del、离开作用域 -1，归零立即释放。 优点是回收即时、没有全局停顿；缺点是处理不了环。

a.b = b; b.a = a 时两者外部引用都没了，计数仍各为 1，永远不归零。 所以 CPython 另有一个循环 GC，只跟踪容器对象，按三代组织。 默认阈值可通过 gc.get_threshold() 查看，是 (700, 10, 10)： 第 0 代净分配数超过 700 触发回收，0 代回收 10 次晋升到第 1 代，第 1 代回收 10 次后扫第 2 代。

  • 整数字符串这类非容器不参与 GC 跟踪，所以大数组不会被反复扫描。
  • 手动回收用 gc.collect()；排查泄漏用 tracemalloc 快照对比，或 gc.get_referrers() 反查谁还抓着对象。
  • __del__ 在环里的析构顺序不确定，清理逻辑应该用 with / contextlib.closing 显式做。

追问：那 C 扩展里为什么会泄漏？（漏写 Py_DECREF，Python 层的 tracemalloc 看不到，要靠 Py_DEBUG 构建 + valgrind/ASAN。）

__dict__ 与 __slots__

面试官会问：什么时候该用 __slots__？

普通实例额外挂一个 __dict__ 存属性：空 dict 本身约 64 字节，有属性后还会扩容， 每个实例都多这一份。定义 __slots__ = ('x', 'y') 后，属性按固定偏移存在对象内部， 每个字段只占一个指针（8 字节），没有 per-instance dict，也禁止动态加属性。

单个对象省不了多少，但构造百万级小对象时（解析 trace、建模大量描述符）差距是数百 MB， GC 扫描也更快。代价是失去灵活性、不支持多继承里都带非空 slots 的组合。

追问：为什么属性访问变快了？（走 member_descriptor 的偏移量，不用查字典；同时拼错属性名会立刻报错。）

GIL

它是什么，保护了什么

面试官会问：说说 GIL。

GIL 是 CPython 的一把全局互斥锁：任意时刻，一个进程里只有一个线程在执行 Python 字节码。 它保护的是解释器内部状态 —— 引用计数、对象分配器、字节码求值循环、C API 的全局结构。

它保护它不保护
引用计数、对象分配、解释器状态你的业务数据。counter += 1 会被拆成 LOAD / ADD / STORE，线程可能在字节码边界被切走

所以“有 GIL 就线程安全”是错的。复合操作还是要自己加 threading.Lock。 GIL 只保证单个字节码不把解释器搞崩。

追问：那多线程还有意义吗？（IO 阻塞、以及调用的 C 扩展/系统调用会释放 GIL，这段时间别的线程能跑。）

为什么存在

面试官会问：为什么不直接去掉 GIL？

  • 根因是引用计数不是线程安全的：ob_refcnt++/-- 是读改写，多线程并发会算错，对象可能被提前释放。
  • 给每个对象加锁会让单线程性能崩溃；全用原子操作在当时代价高、硬件支持也不齐。
  • 用一把大锁保护解释器实现最简单，单线程几乎零成本，C 扩展作者也不需要关心线程安全。

这是单核时代的合理妥协。代价是多核上多线程跑 CPU 密集代码没有加速，甚至因为抢锁更慢。

追问：去 GIL 难在哪？（要同时改引用计数、内存分配器、所有 C 扩展的 ABI，还要保证单线程性能不退化 —— 这就是 PEP 703 的难点。）

切换机制

面试官会问：线程是怎么抢 GIL 的？

持锁线程在求值循环里周期性检查有没有人等待。等待线程设置 drop 请求， 持有者在下一个检查点释放 GIL 并唤醒等待者；交接间隔由 sys.setswitchinterval() 控制， 默认 5ms（sys.getswitchinterval() 返回 0.005）。

  • 切换不是硬实时：走到检查点才让，所以一个长 C 调用不放 GIL 就会卡住所有线程。
  • 高并发下可能出现某线程反复抢到的护航效应；纯计算时线程越多，抢锁开销越大。

追问：为什么 5ms 不调小？（调小响应更好但切换开销上升；调大吞吐更好但延迟变差。属于经验折中。）

怎么绕过

面试官会问：实际工作中你怎么处理 GIL 的限制？

手段做法适用 / 代价
多进程multiprocessing / ProcessPoolExecutor真并行；启动贵、数据要 pickle
扩展里放锁Py_BEGIN_ALLOW_THREADS / Py_END_ALLOW_THREADS纯 C 计算、阻塞式驱动调用；必须保证期间不碰 Python 对象
用释放了 GIL 的库numpy、torch 的算子内部已经放锁重计算场景，线程池也能吃到并行
子解释器3.12+ 每个子解释器可有独立 GIL（PEP 684）隔离插件；生态兼容性有限
Free-threaded 构建3.13 起实验性 --disable-gil（PEP 703）需要所有 C 扩展重新编译并声明支持，暂不适合生产
结合你的场景 “抓多台机器的 log、并发跑采集” → 线程池（IO 等待时释放 GIL）。 “批量跑编译/对比实验” → 进程池（真并行）。 “大矩阵乘、torch 跑推理” → 底层已放锁，线程池即可。 这三句话足够回答“你实际怎么用”。

追问：为什么 numpy 两个线程能并行，而两个 Python 循环不能？（前者在 C 层循环且释放了 GIL，后者全程持有 GIL。）

生成器与状态

yield 到底暂停了什么

面试官会问：生成器和普通函数的区别？状态存在哪？

函数体里出现 yield，调用时就不执行函数体，而是返回一个生成器对象。 每次 next() 执行到下一个 yield 暂停，局部变量和执行位置保存在该生成器自己的栈帧里， 再 next() 从暂停点恢复。所以状态不是靠全局变量，而是每份生成器各有一份。 

def read_chunks(path, size=1 << 20):
    with open(path, "rb") as f:
        while chunk := f.read(size):
            yield chunk

这种写法内存恒定，适合处理上百 GB 的 trace / dmesg / 性能计数。 生成器还支持 send() 传值、throw() 注入异常。

追问：生成器能遍历几次？（一次。耗尽是 StopIteration，要重放就重新创建。）

yield from 与协程的根

面试官会问：yield from 有什么用？async/await 和生成器什么关系？

yield from sub() 把子生成器的产出透明转发出去，send/throw 也会转发， 并且能拿到子生成器的 return 值，比手写 for x in sub(): yield x 更高效。

async/await 复用的就是这套暂停/恢复机制：协程对象实现 __await__（返回迭代器）， await 就是让出控制权、等结果就绪再恢复。区别是协程由事件循环驱动，而生成器由 next() 驱动。

关键点 协程不产生并行，它只在等待 IO 时让出执行权。在协程里跑 CPU 密集或同步阻塞调用， 会卡死整个事件循环 —— 得用 asyncio.to_thread() 或 run_in_executor() 丢出去。

追问：那 GIL 在 asyncio 下还在吗？（在。asyncio 是单线程并发，和 GIL 无关。）

C 扩展与 PyTorch

为什么 GPU 框架的核心是 C++

面试官会问：PyTorch 为什么不全用 Python 写？Python 层是性能瓶颈吗？

PyTorch 是薄 Python 前端 + 厚重 C++ 后端：Python 负责组图、API、调度； 张量内存、算子实现、自动微分都在 C++（ATen/libtorch）和 CUDA kernel 里，Python 只持有句柄。

  • 性能：一次 Python 分发是微秒级，一个大 kernel 是毫秒级，比例可忽略。
  • 控制力：显存布局、异步流、内存池、kernel launch 都需要精确控制，Python 给不了。
  • 复用：C++ 后端能同时服务 Python、C++ 部署和推理引擎。

真正的瓶颈通常在算子太碎、没有融合、或数据在 CPU/GPU 间反复拷贝， 解法是 CUDA Graph、torch.compile，而不是“把 Python 换掉”。

追问：那小算子上为什么 Python 开销会显出来？（每个 op 都要走一次绑定层分发和 kernel launch，几微秒 × 几千个 op 就不可忽略。）

在 C 扩展里安全地释放 GIL

面试官会问：你写过 C 扩展吗？怎么让它在等待时不阻塞其他线程？

扩展函数默认持有 GIL。做纯 C 计算或阻塞式驱动调用时应主动放锁： 

static PyObject *py_submit(PyObject *self, PyObject *args)
{
    int rc;
    Py_BEGIN_ALLOW_THREADS
    rc = drv_submit_and_wait();   /* 阻塞期间别的线程可执行 */
    Py_END_ALLOW_THREADS

    return PyLong_FromLong(rc);
}
铁律 在 Py_BEGIN_ALLOW_THREADS 和 Py_END_ALLOW_THREADS 之间， 不能访问任何 Python 对象、不能调任何 Py* API、不能抛 Python 异常， 因为锁不在你手上，对象可能被别的线程释放。

另外两条规则：返回值 PyObject* 是新引用，调用方负责 Py_DECREF； PyList_GetItem 这类返回借用引用，不能 DECREF。 如果线程是 C 侧创建的，回调 Python 前必须 PyGILState_Ensure()，用完 PyGILState_Release()。

追问：新项目和旧项目分别选什么绑定？（新项目 pybind11 或更轻的 nanobind；只调现成 C 库、不想编译就 ctypes —— 注意 ctypes 调用期间也会释放 GIL。）

高频问答

GIL 是什么、为什么存在、怎么绕过？

CPython 的全局互斥锁，保证同一时刻只有一个线程执行字节码。存在是因为引用计数不是线程安全的，用一把大锁实现最简单、单线程开销最小。

它只保护解释器内部，不保护业务数据。绕过：CPU 密集用多进程；C 扩展用 Py_BEGIN_ALLOW_THREADS；numpy/torch 算子内部已放锁；3.13+ 有实验性的 free-threaded 构建。

加分句：IO 阻塞时释放 GIL，所以线程池对 IO 密集有效；切换间隔默认 5ms。

is 和 == 的区别？

is 比身份（id()，CPython 下是地址），== 比值（__eq__）。

is 只用于 None、True/False 和哨兵。小整数缓存（-5~256）和字符串驻留会让某些字面量 is 为 True，但这是实现细节，不能依赖。

深拷贝与浅拷贝？

浅拷贝 copy.copy() 只复制最外层容器，内层对象仍共享；深拷贝 copy.deepcopy() 递归复制，得到完全独立的一份。

a = b 连浅拷贝都不是，只是多了一个引用。深拷贝能处理循环引用（内部用 memo），但很慢；含文件句柄、锁的对象通常无法深拷贝。

装饰器的原理？写一个。

本质是“接收函数、返回新函数”的高阶函数，@deco 等价于 f = deco(f)。用 functools.wraps 保留元信息。

import functools, time

def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__}: {time.perf_counter()-t0:.4f}s")
    return wrapper

带参数的装饰器要多包一层：@retry(3) 实际是 retry(3)(f)。驱动测试里常用来做超时打印、ioctl 自动重试。

生成器和迭代器的区别？

迭代器实现 __iter__ / __next__；生成器是 yield 自动生成的迭代器，不用手写协议，状态由栈帧保存，支持 send() 双向通信。

共同点：只能遍历一次。区别在写法与灵活性，不在能力边界。

为什么 PyTorch 的 Python 层不是瓶颈？

算子和张量管理都在 C++/CUDA 层，Python 只是薄分发层。一次 Python 调用的开销远小于一个 kernel 的执行时间。

例外：算子太碎时分发开销累积，用 CUDA Graph / torch.compile 合并；数据加载写不好（Python 循环、频繁 H2D/D2H 拷贝）也会成为真瓶颈。
