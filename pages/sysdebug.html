调试与性能分析

NVIDIA 虚拟化的 JD 明确写了 GDB / KGDB / ftrace / perf 定位复杂内核问题。 但面试官不考你背参数 —— 考的是拿到一个从没见过的现场，你怎么一步步缩小范围。 这一页只保留「能讲出判断逻辑」的部分：什么症状、用哪个工具、看哪个信号、下一步做什么。

这一页怎么用 先读 方法论，它是所有工具的组织方式；其余章节按你被问到的场景跳读。 每一小节最后的「追问」就是面试官会接着问的那一句，先自己答一遍。

追问：「你说用 ASan，它为什么能看到越界？开销多少？线上能开吗？」 —— 答不上原理就说明只是会用工具。每类工具都要知道它插了什么、慢在哪、能不能上生产。

GDB

GDB 在驱动岗的价值不在「会打断点」，而在两件事：读崩溃现场（core）， 以及附加到正在跑的进程。这两件事决定了你能不能处理线上问题。

崩溃现场：core 与栈的读法

ulimit -c unlimited                        # 默认常是 0，先放开
echo '/var/crash/core.%e.%p.%t' > /proc/sys/kernel/core_pattern

gdb ./app /var/crash/core.app.1234.1700000000
(gdb) bt                    # 第 0 帧是出错点，越往下越靠近 main
(gdb) bt full               # 每帧附带局部变量
(gdb) frame 1                # 栈顶在 libc 里时，看调用它的那一帧
(gdb) info registers
(gdb) x/16gx $rsp           # 栈内存，排查栈被踩
(gdb) info threads

读栈的关键判断：第 0 帧在 memcpy/free/strlen 里，问题通常不在 libc， 而是第 1 帧传进去的指针已经坏了。core 必须和产生它的二进制、共享库版本严格一致，否则栈是错的。 如果系统用 systemd-coredump，coredumpctl list + coredumpctl gdb <pid> 直接进调试器。

追问：「attach 一个进程为什么它停住了？为什么 attach 不了 D 状态的进程？」 —— ptrace(PTRACE_ATTACH) 让目标收到 SIGSTOP；D 状态在不可中断睡眠中， 信号都投递不进去，所以只能看 /proc/<pid>/stack。

优化后的代码怎么调

这是区分度最高的一点。-O2 之后变量被放入寄存器、复用甚至消除， p var 经常返回 <optimized out>。正确做法不是退回 -O0（行为可能变）， 而是 -Og：为调试优化，保留可读性的同时接近真实执行。 再加 -fno-omit-frame-pointer，否则栈回溯会断（perf 也依赖它）。 

(gdb) disassemble /m my_func    # 汇编与源码交错
(gdb) p/x $rax                  # 变量此刻可能就在某个寄存器

真要强力调试时，dprintf handle_io, "fd=%d\n", fd 比断点更轻 —— 不暂停、只打印。 把一组断点和打印命令写进脚本，用 gdb -x init.gdb 加载，就是一个轻量的定向打印方案 （代价是每次命中都要进内核 ptrace，高频路径别用）。 GDB 的 Python pretty-printer 能让 STL 容器直接打印；内核侧则是 vmlinux-gdb.py 提供的 lx-ps、lx-dmesg。

追问：「为什么 -g 和 -O2 一起用，栈还是能看但变量没了？」 —— 栈帧布局由 ABI 和 CFI 保证，调试信息还在；变量被优化进寄存器后，DWARF 里只有「某个位置表达式」， gdb 找不到确定的存储位置就报 optimized out。

多线程与远程调试

(gdb) thread apply all bt       # 死锁排查第一招
(gdb) set scheduler-locking on  # 只让当前线程跑，调竞态必备
(gdb) catch syscall write       # 在系统调用处断住

# 远程：目标机 gdbserver，宿主机 gdb
gdbserver :1234 ./app
gdb ./app -ex 'target remote 192.168.1.10:1234'

# QEMU 内核调试：-s 等价 -gdb tcp::1234，-S 表示启动即冻结
gdb vmlinux -ex 'target remote :1234'

scheduler-locking 是很多人不知道的开关：默认单步时其他线程还在跑， 你盯的变量会被别人改掉，看起来像灵异事件。调竞态先把它冻住。

追问：「detach 和 quit 有什么区别？」 —— detach 断开但让进程继续；quit 在 attach 场景下会杀掉进程，事故现场别乱敲。

内核调试

内核出错比用户态可怕：一个进程崩只死一个进程，内核崩死整机，而且现场默认不保留。 这一节的核心问题其实是「怎么把现场留下来」。

读懂 oops

BUG: unable to handle kernel NULL pointer dereference at 0000000000000048
RIP: 0010:my_driver_probe+0x1a/0x3f0 [my_driver]
Call Trace:
 <TASK>
 ? my_driver_probe+0x1a/0x3f0 [my_driver]
 pci_device_probe+0x8e/0x140
 really_probe+0x1c5/0x2a0
  • RIP 是出错指令地址。func+0x1a/0x3f0 表示函数内偏移 0x1a、函数总长 0x3f0。
  • 还原源码行：gdb vmlinux -ex 'list *(my_driver_probe+0x1a)'，或 objdump -dS my_driver.ko。
  • Call Trace 里的 ? 表示该帧不可靠（栈被破坏或优化过），不能当事实用。
  • 地址是 0x48 这种小值，通常是 NULL 指针 + 结构体成员偏移 —— 先找那个指针为什么是 NULL。
  • 日志里第一条 error 才是根因，后面的报错往往是连锁反应。

追问：「为什么 Call Trace 会有 ?？」——x86 上内核用 frame pointer 回溯， 编译器省略 FP、或栈被踩坏时，回溯器只能猜；CONFIG_UNWINDER_ORC 用生成的 unwind 表更可靠， 但跨异常栈仍可能不准。

BUG_ON、WARN_ON 与 panic()

接口触发后该用在哪
WARN_ON(cond)打印调用栈，继续运行不变量被破坏但还能继续；线上首选
BUG_ON(cond)打印 oops，杀掉当前进程；在中断上下文里可能直接 panic不可恢复的逻辑错误，线上基本禁用
panic()整机停机真的没救了，配合 kdump 收现场

社区在持续移除 BUG_ON：一个用户能触发的错误就能变成拒绝服务。正确做法是返回错误码， 或者降级成 WARN_ON_ONCE。

追问：「WARN_ON 在中断上下文里安全吗？」——安全，它不睡眠； 但高频 WARN 会拖垮系统（每次都要抓栈），所以线上要用 _ONCE 变体。

把现场留下来：kdump、sysrq、pstore

kdump 预留一小块内存跑 crash kernel，主内核 panic 后 kexec 跳过去， 把整个内存 dump 成 vmcore。之后用 crash 离线分析： 

cat /proc/cmdline                 # 应有 crashkernel=256M 之类的预留
systemctl status kdump

crash /usr/lib/debug/lib/modules/$(uname -r)/vmlinux /var/crash/vmcore
crash> bt            # panic 时的任务栈
crash> log           # 完整内核日志，比屏幕上的多
crash> ps            # 崩溃时刻所有进程
crash> foreach bt    # 所有任务栈，查 hung

sysrq 是不重启也能取证的开关： echo t > /proc/sysrq-trigger 打印所有 CPU 的调用栈和所有任务栈； echo w 只列出 blocked（D 状态）任务；echo l 给所有 CPU 发 NMI 打印栈； echo c 主动 panic 交给 kdump。顺序很重要：先取证，再杀。

pstore / ramoops 把 panic 前的日志写进不掉电的 RAM，重启后从 /sys/fs/pstore/ 读出。设备侧（车载、手机）用户不会接串口，这是唯一能拿到的现场。

追问：「dmesg 为什么可能丢日志？」——printk 是 lockless ring buffer， 缓冲区满了会覆盖；崩溃瞬间没刷出去的部分直接没了，所以要有 pstore。 另外很多系统 dmesg_restrict=1，普通用户读不到。

卡死：hung task 与 lockdep

hung task：内核 khungtaskd 定期扫描处于 TASK_UNINTERRUPTIBLE 超过 /proc/sys/kernel/hung_task_timeout_secs（默认 120 秒）的任务并打印栈。 看到 INFO: task X blocked for more than N seconds，重点看它卡在哪个函数、在等什么。 驱动里最常见的原因：在中断上下文里睡眠、等一个永远不会到来的 completion。

lockdep 是锁依赖图检查器，即使这次没真死锁，也会把「可能成环的加锁顺序」提前报出来： 

WARNING: possible circular locking dependency detected
------------------------------------------------------
kworker/0:1/123 is trying to acquire lock:
 (&dev->lock){+.+.}, at: dev_write+0x30/0x80

but task is already holding lock:
 (&global_lock){+.+.}, at: dev_read+0x20/0x60

 Possible unsafe locking scenario:
       CPU0                    CPU1
       ----                    ----
  lock(&global_lock);
                               lock(&dev->lock);
                               lock(&global_lock);
  lock(&dev->lock);

读法只有两步：「trying to acquire」和「already holding」两段合起来就是一个环； 下面的 unsafe locking scenario 把这个环画出来了，照着改加锁顺序即可。 花括号里是锁的上下文/中断状态标记，用于判断是否可能在中断里重入。 开 lockdep 内核会慢数倍，只在调试内核开。

追问：「用户态死锁没有 lockdep 怎么办？」——thread apply all bt 看每个线程停在哪个锁等待上，把「持有 → 等待」连成图看有没有环； 再配合 /proc/<pid>/syscall 或 strace -p 确认它卡在 futex。

ftrace 与 tracepoint

ftrace 是内核内置的追踪框架，不用装东西、不用重编内核，通过 debugfs 操作。 它的最佳场景是：问题偶发，但你知道该盯哪几个函数或事件。

配置流程

cd /sys/kernel/debug/tracing      # 新内核也可能是 /sys/kernel/tracing

cat available_tracers             # function function_graph nop ...
echo nop > current_tracer         # 换 tracer 前必须先回到 nop

echo 'my_driver_ioctl' > set_ftrace_filter   # 只追踪它，开销立刻降下来
echo function_graph > current_tracer
echo 1 > tracing_on
# ... 复现 ...
echo 0 > tracing_on
cat trace

trace 是缓冲区快照，读完不清空；trace_pipe 是消费式的， 适合 tail -f 实时观察偶发问题。两者用途不同，别混。

追问：「为什么 set_ftrace_filter 这么重要？」——function tracer 给所有函数入口插桩，全开能带来几十个百分点的开销，还会把真正的问题淹掉。

function_graph 与 tracepoint

function_graph 画出调用树并标注每个函数耗时，是找「哪一层慢」最快的办法。 用 set_graph_function 限定子树。输出里 + 标记耗时超过 10 微秒， ! 超过 100 微秒，# 超过 1 毫秒（由 funcgraph-overhead 选项控制显隐）： 

echo 'vfs_read' > set_graph_function
#  0) + 12.345 us   |    my_read();
#  0)   0.512 us    |    rw_verify_area();

# tracepoint：内核预埋的事件，语义稳定、开销低
echo 1 > events/sched/sched_switch/enable
echo 1 > events/irq/enable

sched_switch 是分析延迟的神器：它记录了谁把 CPU 让给谁、前一个任务是什么状态 （prev_state 是 D 还是 R）—— off-CPU 时间就是从这里算出来的。 文本操作太啰嗦时用 trace-cmd record -p function_graph -l my_func -- ./app， 再 kernelshark 看时间线。

追问：「ftrace 和 perf 是什么关系？」——ftrace 是内核内的 tracing 框架，事件驱动、每次发生都记； perf 主要基于 PMU 采样，但也能读 tracepoint（-e sched:sched_switch）。 两者不是竞品，短事件用 ftrace / eBPF，统计热点用 perf。

perf 与 eBPF

perf stat：先拿宏观指标

perf stat -e cycles,instructions,cache-misses,branch-misses ./app
#   1,234,567,890   cycles
#     987,654,321   instructions   # 0.80 insn per cycle
  • IPC = instructions / cycles。IPC 低说明 CPU 在等（cache miss、分支预测失败、内存延迟）；
  • IPC 不低但程序慢，说明指令太多，是算法层面的问题，优化方向完全不同；
  • cache-misses 占比高 = 数据局部性差；branch-misses 高 = 分支不可预测。

追问：「IPC 0.8 说明什么？」——不能单独下结论。要看 CPU 基线（不同微架构差异大）、 是否超线程共享、以及 %usr 是否真的高。IPC 只是「每周期退休多少指令」，必须结合 cache 和 stall 指标一起读。

perf record：定位到函数，以及采样为什么会骗你

perf record -F 999 -g --call-graph dwarf -o perf.data -- ./app
perf report --stdio --sort=dso,symbol
perf top -p 12345
perf trace -p 12345        # 基于 tracepoint 看系统调用耗时，比 strace 开销低

原理：PMU 计数器溢出触发中断，内核在中断里记录当前 IP 和调用栈。 所以它是概率采样：函数耗时占比约等于出现比例。 三个必须知道的偏差来源：

  • 短函数采不到：只跑 1 微秒的函数，在 1000Hz 下基本不出现。要么提高频率，要么用 ftrace / eBPF 的事件驱动方式。
  • skid（滑移）：中断到达时 CPU 已经走过几条指令，热点会偏向后一条指令，看汇编时要容忍。
  • 栈展开方式：默认 fp 依赖 -fno-omit-frame-pointer，否则栈是断的； --call-graph dwarf 更准但每次采样都要查 unwind 表，慢且数据大。

追问：「perf report 里大量 [unknown] 怎么回事？」 —— 通常是栈展开失败（省了 frame pointer 或 DWARF 不匹配），或者二进制没有符号； 先 perf buildid-cache 补符号，再换 --call-graph dwarf。

火焰图：on-CPU 与 off-CPU

perf record -F 999 -g -- sleep 30
perf script > out.perf
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl out.folded > flame.svg

读法：横轴是采样频率（不是时间），宽度代表占比，纵轴是调用深度。 找最宽的「平顶」——那是自己吃满 CPU 的函数。

第一个分叉点：on-CPU 还是 off-CPU 上面的火焰图只包含在 CPU 上跑的时间。如果程序慢在等 IO / 等锁， on-CPU 图会显得「很干净」——因为它根本没在跑。此时要画 off-CPU： 用 BCC 的 offcputime（或 bpftrace 在 sched_switch 上统计阻塞栈）。 「CPU 不忙但程序慢」= off-CPU 问题，这是排查的第一次分叉。

追问：「火焰图能不能看出内存带宽瓶颈？」——不能直接看出。它只给时间分布， 带宽问题要配合 perf stat 的 cache-misses 或 perf mem 才能确认。

bpftrace：让内核按你的问题报数

# openat 的延迟分布（纳秒直方图）；用 tracepoint 最稳，不依赖内核内部函数名
bpftrace -e '
tracepoint:syscalls:sys_enter_openat { @start[tid] = nsecs; }
tracepoint:syscalls:sys_exit_openat /@start[tid]/ {
  @ns = hist(nsecs - @start[tid]); delete(@start[tid]);
}'

# 谁在 open，按进程计数
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'

它能上生产的关键是 eBPF verifier：加载前静态检查所有路径 —— 不允许越界访问、不允许无界循环、不允许读未初始化内存，通过后才 JIT 挂到 hook 上。 所以它比内核模块安全得多。内核版本太老或没有 BTF 时只能用 ftrace。

追问：「eBPF 能完全替代 ftrace 吗？」——不能。ftrace 是内核原生、无需编译， 在最小化环境里更可靠；eBPF 更灵活但依赖内核版本、BTF 和额外工具链。

内存问题

内存问题的特点是症状和原因隔得很远：分配在这里，崩溃在几百行之后。 所有工具的目标都只有一个：把分配点和崩溃点关联起来。

用户态：先选工具，再看信号

工具管什么原理 / 开销什么时候用
valgrind memcheck越界、use-after-free、未初始化读、泄漏动态二进制翻译，慢 20-50 倍拿到已编好的二进制、要最全的检查
ASan堆/栈/全局越界、use-after-free编译期插桩 + 红区，约 2x，内存 2-3x测试环境首选，只检查真正执行到的路径
LSan内存泄漏退出时扫描不可达但未释放的块，开销低常和 ASan 一起开
UBSan未定义行为（有符号溢出、空指针、对齐）编译期检查，约 1.2xCI 常驻
TSan数据竞争记录访问 + happens-before 图，5-15x并发 bug，见 并发

g++ -fsanitize=address,undefined -fno-omit-frame-pointer -g app.cc
# 报错会同时给出：freed by 的栈 + previously allocated by 的栈

注意 ASan 和 valgrind 不能同时开，两者都接管内存管理，会互相打架。 Python 侧用标准库的 tracemalloc：tracemalloc.start() 后在两个时间点取 snapshot() 做 diff，按行号看谁在增长，不用装额外工具。

追问：「RSS 一直涨一定是泄漏吗？」——不一定。glibc arena 不归还、page cache、 内存碎片都会让 RSS 涨。要区分单调上涨且反复触发后不回落，才是泄漏。

内核：KASAN 与泄漏检测

KASAN 是内核版 ASan，用影子内存标记每 8 字节是否可访问，每次访问插桩检查。 开销约 CPU 2-3 倍、内存 1/8（影子比例 1:8），驱动开发时几乎必开。 抓 use-after-free、越界、栈溢出都比事后猜可靠得多。

  • KFENCE：采样版检测器，开销低到可以上生产，适合抓偶发越界。
  • KCSAN：内核数据竞争检测，原理类似 TSan。
  • kmemleak：扫描「分配了但没有指针指向」的内存，echo scan > /sys/kernel/debug/kmemleak 后读结果；内核会变慢，只在调试内核开。
  • slab 泄漏：slabtop -s c（按 cache 大小排序），或 watch -n 1 'grep my_cache /proc/slabinfo'，看哪个 cache 持续增长。

追问：「为什么 KASAN 能立刻抓到 use-after-free，而普通内核可能跑几天才崩？」 —— 释放的内存不会立刻被复用，普通内核里那块内容可能一直是旧值，读它「看起来正常」； KASAN 在释放时就把影子标记为不可访问，下一次访问立即报错。

OOM killer 日志怎么读

Out of memory: Killed process 1234 (python) total-vm:8388608kB,
anon-rss:4194304kB, file-rss:0kB, shmem-rss:0kB

看四件事：杀的是谁（名字 + RSS）、它为什么分高 （oom_score 大致正比于内存占用，再加上 oom_score_adj）、 当时内存状态（往前翻 dmesg 的 meminfo）、是不是 cgroup 限制 （容器里可能是 memory cgroup OOM，不是整机内存不够）。

/proc/meminfo 只看两个字段就够定位：MemAvailable（真正可用， 已把可回收的 page cache / slab 算进去，比 MemFree 靠谱）和 Dirty（待写回，过高会卡 IO）。

追问：「MemFree 很低但系统很健康，正常吗？」——正常，Linux 会主动用空闲内存做缓存； 判断内存是否不足要看 MemAvailable 和有没有发生回收/swap。

并发问题定位

并发问题的本质难点是不可复现。工具只有两类： 检测器（TSan / KCSAN，告诉你「这里有竞争」）和 复现器（stress、rr，把偶发变成必然）。

死锁：先确认环，再谈避免

确认顺序：① ps -eo pid,stat,wchan:32,cmd 找出 D 状态； ② gdb -p + thread apply all bt（或内核侧 sysrq w / crash foreach bt）拿所有栈； ③ 把「持有锁 → 等待锁」连成图，看有没有环；④ 内核侧直接看 lockdep 画出的环。

避免：全局定义加锁顺序并强制遵守；一次性锁多个用 std::lock； 用 scope 限制持锁时间；拿不到锁时有超时/退避；内核里开发期始终开 lockdep。

追问：「加锁顺序文档写了，为什么还会出问题？」——跨模块调用时没人强制执行， 只能靠工具检查。能主动说「我们用 lockdep / 静态检查来保证顺序」，比背四要素强。

数据竞争：TSan、KCSAN 与 atomic 误用

g++ -fsanitize=thread -g app.cc -o app    # 用户态 TSan
# 报告会给出「哪次写」「哪次读」并发，以及双方调用栈

TSan 给每次内存访问打时间戳、维护 happens-before 图，没有同步关系的并发访问就报。 它会把所有未加锁的地方都报出来，需要自己判断哪些真正影响正确性 （比如纯统计计数，可能无害但仍算竞争）。

内核侧用 KCSAN（CONFIG_KCSAN=y），报 BUG: KCSAN: data-race in ...。 最常见的误用不是「忘了 atomic」，而是以为 atomic 能保护复合操作： if (x.load() == 0) x.store(1); 是两次原子操作，两个线程能同时进； 以及把 seq_cst 随手改成 relaxed 却没有正确的同步语义。

追问：「TSan 报的竞争一定要修吗？」——要看是否存在 happens-before 之外的同步 （比如靠信号量、或者只在启动阶段访问）。但不能靠「看起来没事」来放过， 要么加同步，要么用 atomic 明确标注。

复现：把偶发变成必然

rr record ./app
rr replay
(rr) reverse-continue        # 反向执行，从崩溃点往回追
  • rr：记录一次执行的所有非确定性输入（调度、系统调用返回值、信号），之后可反复重放、还能倒着走。对多核和 GPU 交互支持有限，但 CPU 侧的竞态几乎是杀手锏。
  • 压力：stress-ng --cpu 8 --io 4 --vm 2 制造竞争窗口，把 1 天 1 次变成 1 分钟 1 次。
  • 固定变量：taskset 绑核、固定随机种子、关频率调节，减少不确定性。
  • 加检测器：KASAN / TSan 把「静默损坏」变成「当场报错」。

追问：「rr 为什么能倒着执行？」——它记录了每个线程的执行顺序和外部输入， 重放时在每个检查点保留快照，反向执行靠恢复最近快照再正向跑到目标点，对用户透明。

GPU 性能分析

GPU 程序慢，第一步永远是分叉：CPU 没喂饱 GPU，还是 GPU 自己算得慢？ 前者用 Nsight Systems 看时间线，后者用 Nsight Compute 看单个 kernel。

Nsight Systems：先看时间线

nsys profile -o report --trace=cuda,nvtx,osrt ./app
nsys stats report.nsys-rep

看三条泳道：CPU 的 API 调用、GPU 的 kernel 执行、显存拷贝。判断规则：

  • GPU 泳道大段空白、CPU 在忙 → CPU 端瓶颈（launch 开销、Python、其他计算）；
  • CPU 卡在 cudaDeviceSynchronize 或 cudaMemcpy → 同步/传输瓶颈；
  • kernel 之间只有微小间隙 → launch 开销，考虑 CUDA Graphs 或融合 kernel；
  • 拷贝与计算串行 → 多 stream + pinned memory 做重叠。

追问：「怎么区分 launch 开销和 kernel 真的慢？」——看时间线：GPU 上空隙明显且 kernel 本身很短， 就是 launch 开销；kernel 占满时间就进 ncu 看内部。

Nsight Compute：单 kernel 的三个指标

ncu -k my_kernel --launch-count 1 --set full ./app
ncu --metrics sm__throughput.avg.pct_of_peak_sustained_elapsed \
        dram__throughput.avg.pct_of_peak_sustained_elapsed ./app
指标含义低说明什么
Compute / SM 利用率计算单元有多忙算得不多，或在等内存
Memory Throughput显存 / L2 带宽用了多少不是带宽瓶颈
Occupancy实际活跃 warp / 理论最大隐藏不了延迟；查寄存器、shared memory、block size

判断顺序：SM 低 + Memory 高 = 带宽瓶颈（合并访问、shared memory、减少重复读）； SM 低 + Memory 低 + Occupancy 低 = 占用率不足（减寄存器、调 block）； SM 高 = 计算瓶颈（改算法或指令）。

追问：「nvidia-smi 显示 100% 利用率，为什么程序还是慢？」 —— 那个 util 的含义是「采样周期内是否有 kernel 在跑」，一个 block 的 kernel 也能让它显示 100%。 它衡量忙不忙，不衡量效率，真正的效率要看 SM 效率和带宽。

常见瓶颈与假象

  • 隐式同步：cudaMalloc、cudaFree、默认的 cudaMemcpy 都可能同步，打断流水。
  • PCIe 往返：host-device 来回搬数据；用 pinned memory、减少拷贝、考虑 Unified Memory。
  • 访存不合并：coalescing 差、bank conflict，带宽看起来满但有效吞吐低。
  • occupancy 低：--ptxas-options=-v 看寄存器和 shared memory 用量。
  • 降频：nvidia-smi -q -d PERFORMANCE 看是否 throttle（功耗/温度）。

现场观测用 nvidia-smi dmon -s pucvmet（功耗、利用率、显存、温度、时钟）， 拓扑用 nvidia-smi topo -m（NV# = NVLink，SYS = 跨 NUMA）。

追问：「GPU 利用率高但吞吐上不去，可能是哪些原因？」 —— 先从「有效带宽 / 有效算力」而不是「util」出发：访存不合并、occupancy 不足、 kernel 太小导致调度开销占比高、或者被 CPU 侧的同步切碎了。

方法论（最重要的一节）

前面都是工具。资深面试真正考的是：没有现成工具能解的问题，你怎么办。 下面几条可以直接背，也真的管用。

先分层，不要一上来就 gdb

层最便宜的确认手段典型现象
应用逻辑日志、线程栈死循环、等一个永不满足的条件
运行时 / 库strace / ltrace卡在某个 futex / read
内核 / 驱动D 状态、sysrq t、dmesg卡在 ioctl、等锁、等 DMA
硬件 / 固件dmesg、nvidia-smi -q掉卡、降频、PCIe 错误

第一步永远是用最便宜的手段确定层：ps 看状态、strace -p 看最后停在哪、 dmesg 看有没有报错。定位到层，问题就解决了一半；在错误的层上折腾 gdb 纯属浪费。

测量代替猜测

「我觉得是内存带宽」「我觉得是锁竞争」——面试里最减分的就是这种话。 正确姿势是先说假设，再说怎么验证： 「我怀疑是 cache miss，所以先跑 perf stat -e cache-misses； 如果占比高，再用 perf record -e LLC-load-misses -g 找具体位置。」

一个可复用的回答模板 假设：我认为瓶颈在 X。
证据：用 Y 工具测，Z 指标是 A（基线是 B）。
验证：如果改成 C，指标应该变成 D；实测吻合，所以假设成立。
按这个结构说话，面试官听到的是工程师，不是工具使用者。

二分法与最小复现

  • 代码二分：git bisect 定位引入问题的 commit。
  • 配置 / 环境二分：换机器、内核、驱动、CPU 型号；一次只改一个变量。
  • 输入二分：缩小数据规模、线程数、场景，直到剩下最小可复现的输入。

花 20% 的时间做一个稳定的最小复现，能省下 80% 的调试时间。 驱动问题尤其如此：一个几十行的 ioctl 测试程序 + 循环脚本， 能把「一天一次」变成「一分钟一次」，之后所有工具才真正可用。

记录时间线与读日志

被问「线上昨天开始变慢，怎么查」，第一个动作应该是问： 什么时候开始的？之前改了什么？ 部署、配置、内核 / 驱动升级、流量变化、硬件更换 —— 这六个变量的时间点对上问题出现的时间点， 往往比任何 profiling 都快。

最常犯的错误：盯着最密集的日志 一堆错误里，第一条才是根因，后面多是连锁反应。 比如内存分配失败导致后续全报空指针，真正要查的是第一条 ENOMEM。 顺序应该是：按时间正序找到第一处异常 → 看它前后上下文 （dmesg -T | less、journalctl -k --since）→ 再统计数量。

USE 与 RED

USE（资源视角）

对每个资源（CPU、内存、磁盘、网卡、GPU）各看三个维度，任一异常就往下钻。

Utilization使用率
Saturation排队/积压
Errors错误计数

RED（服务视角）

对每个服务或接口各看三个维度，适合定位「用户感知的慢」在哪里。

Rate请求速率
Errors错误率
Duration延迟分布

USE 找「哪个资源是瓶颈」，RED 找「哪个服务/接口是瓶颈」，两个一起用覆盖面才完整。

追问：「给你一个从没见过的线上问题，前 10 分钟怎么用？」 —— 好答案的顺序是：确认影响面 → 看时间线 → 分层 → 再上工具； 并且要主动说出「先止血（回滚/限流/重启），再定位」。 一上来就说「我用 gdb」的，通常没真正处理过线上事故。

高频问答

进程 hang 住了，你怎么排查？

看状态：ps -o pid,stat,wchan:32,cmd -p <pid>。 R = 死循环在跑，D = 卡在内核（等 IO/锁），S = 正常睡眠等待。

看栈：用户态 gdb -p + thread apply all bt； D 状态 attach 不上时看 /proc/<pid>/stack 和 /proc/<pid>/wchan。

看系统调用：strace -p 或 cat /proc/<pid>/syscall，确认它停在哪个调用。

看依赖：所有线程都在 futex → 死锁或活锁；等网络 → 对端没响应；D 状态 + 磁盘 → IO。

追问点：能说清「怎么区分死锁和仅仅在等 IO」，比背命令重要。

内核 panic 了，怎么定位到具体代码行？

拿现场：dmesg / 串口 / pstore；有 kdump 就 crash vmlinux vmcore， 用 bt 和 log 拿完整日志。

读 RIP：func+0x1a/0x3f0 给出函数内偏移，用 gdb vmlinux -ex 'list *(func+0x1a)' 或 objdump -dS vmlinux 还原到源码行。

读 Call Trace：? 标记的帧不可靠；地址是小值（如 0x48）通常是 NULL + 成员偏移，去找那个指针为什么为 NULL。

看 panic 之前：往往先有 WARNING / BUG / lockdep 报告，真正的根因在几条日志之前。

怎么证明一个性能问题是 CPU 还是 IO 瓶颈？

先看 CPU 忙不忙：mpstat -P ALL 1。%usr + %sys 都低， 说明在等 —— 那就是 IO 或锁。

看 on-CPU 火焰图：perf record -g 采到的栈很薄， 说明进程大部分时间不在 CPU 上 → off-CPU 问题。

看等待：pidstat -u -d 1 看 %wait/iowait； iostat -x 1 看磁盘 %util 和 await。

做对照：把 IO 换成缓存命中，如果显著变快就是 IO；加并发后 CPU 满了但吞吐不涨， 说明瓶颈不在 CPU。

算 IPC：perf stat 的 IPC 高但慢 = 指令多；IPC 低 = 在等内存/cache/分支。

perf 采样不准怎么办？

先认清这是采样本质：短函数采不到、热点偏向后一条指令（skid），不是 bug。

提高频率：-F 9999，但受 /proc/sys/kernel/perf_event_max_sample_rate 限制，且开销上升。

换事件源：-e cpu-clock 或 -e cycles:u 只统计用户态。

换方法：短函数/事件型问题用 ftrace / bpftrace，事件驱动、不依赖采样。

查栈展开：大量 [unknown] 说明 fp 展开失败，换 --call-graph dwarf 或补符号。

内存泄漏怎么查？

先确认是泄漏：反复触发后 RSS 单调上涨且不回落；区分 page cache / arena 可回收占用。

用户态：测试环境用 ASan + LSan（快、给分配栈），或 valgrind --leak-check=full（最全但慢）； 线上可采样或用 heaptrack。

内核态：/proc/slabinfo / slabtop -s c 看增长的 cache； kmemleak 扫描不可达分配；slub_debug 检查越界。

核心：找到分配点而不是盯着内存增长，确认每条分配路径都有对应释放。

死锁怎么确认、怎么避免？

确认：所有线程停在锁等待（futex / __lll_lock_wait）， 且「持有 → 等待」能连成环。内核里 lockdep 直接画出环；用户态靠 thread apply all bt 人工分析。

区分活锁：死锁是大家不动；活锁是都在跑但没进展（不停让出、重试）。

避免：全局加锁顺序；std::lock 一次性锁多个；scope 限制持锁范围； 超时/退避；内核里始终开 lockdep。

追问点：为什么「文档写了顺序」还会出问题？因为跨模块调用无人强制 —— 要靠工具。

GPU 程序比预期慢，你怎么定位？

先分叉：nsys 看时间线，判断是 CPU 提交、数据传输，还是 GPU 执行慢。

CPU 侧：频繁同步（cudaDeviceSynchronize、隐式同步的 cudaMemcpy/cudaMalloc）、 kernel 太小 launch 太频繁、Python/GIL 拖慢。用 stream、pinned memory、CUDA Graphs 修。

GPU 侧：ncu 看 SM 利用率、显存带宽、occupancy： SM 低 + Mem 高 = 带宽；SM 低 + Occupancy 低 = 占用率；SM 高 = 计算。

别被假象骗：nvidia-smi 的 100% 只是「有 kernel 在跑」，不代表高效。
